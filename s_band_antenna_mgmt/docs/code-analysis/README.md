## 三句话结论

1. **代码能跑，但"跑成功"不等于"做成功"**：38 个函数是假实现（15 个纯桩 + 2 个空壳 + 21 个吞错误），20 处用"命令已发出"冒充"操作已成功"，北向应答里的 `result` 字段大量是硬编码字面量 0。BBU 侧看到的"成功"有相当比例不反映硬件真实状态。

2. **有三类问题会在现场造成实际损害，且已在 57MB 部署日志中留下证据**：小区配置去重陷阱（**现场真实触发至少 541 次**，BBU 以为配好了、天线实际没配）、心跳超时兜底被 `heartbeat_start()` 清零绕过、以及 BBU 可用一个 4 字节畸形 IE 让接收线程 100% CPU 死循环（4 处 TLV 遍历缺下界校验）。

3. **北向链路零认证 + 透传通道可裸写 FPGA + 两处由 BBU 可控字符串拼出的 shell 命令**（`popen("tar -xzf ...")`、`system("rm -rf ...")`），在 `User=root` 下构成 root 级远程命令执行路径。这不是理论风险，是代码里现成的调用链。

## 交付阻断判断（评审关注）

**建议：不建议按当前状态交付。** 依据见 [01-执行摘要](01-执行摘要.md) §4。

阻断项集中在三处：

- **安全**：root 级远程命令执行（2 处命令注入 + 零身份校验 + 透传裸写）
- **可用性**：远程可触发的死循环 DoS（4 处），且触发后进程无法优雅退出（`pthread_join` 永久阻塞，只能 `kill -9`）
- **正确性**：复位、校准、环回三个运维动作是假的（返回成功但没执行），版本升级闭环断裂（上注结果从不回报），带宽单位在四种解释下都无法自洽且 FPGA 侧无拒绝机制

## ⚠️ 三件必须先知道的事

### 1. Cross-check 阶段有 2 项失败，结论存在未覆盖面

`e2e-flow`（端到端流程梳理）和 `completeness`（覆盖度核查）两个 agent 失败，无产出。详见 [02-方法与数据来源 §5](02-方法与数据来源.md)。

**影响**：
- 端到端流程是靠 [07-架构与数据流](07-架构与数据流.md) 里的 5 条数据流（A~E）拼出来的，**没有一份独立 agent 做过完整的跨子系统时序核查**。数据流之间的相互影响（例如上注期间业务面会怎样）存在覆盖空白。
- 覆盖度由 `completeness-critic` 部分补上（它评估了已有材料的维度覆盖，并派生了 Gap 阶段的 9 项深挖），但**"还有哪些没查"这个问题没有被系统回答**。

因此本报告的问题清单应理解为**下界**，不是全集。

### 2. `cell_config.c` 的修复已被回退，当前代码仍有 P0-4 缺陷

工作流期间源码被改动过（agent 自己记录了这一点）。本次复核发现：

| 位置 | mtime | 大小 | 是否含 `sent_to_antenna` 修复 |
|---|---|---|---|
| `rollback_backup/cell_config.{c,h}.modified` | 2026-09-22 08:52 | 29924 B | ✅ 有（含"僵尸记录"注释） |
| `src/cell_config.c` / `include/cell_config.h` | 2026-09-22 08:53~08:55 | 26403 B | ❌ **无** |

当前 `src/cell_config.c:402-415` 仍在模式检查失败时写入本地表（`active=true`），`:426-441` 的去重循环仍只比 `dl/ul/bw`、**不比 `beam_id`、不查是否真下发过**，`has_any_freq()`（`:13-21`）也只看 `active`。

**后果**：现场触发 541 次的那个缺陷，在当前代码里仍然存在；且"僵尸记录"会继续支撑 `update_tx_control()` 保持发射开启。

修复版就在 `rollback_backup/` 里，恢复它是最省事的路径。

### 3. 行号时效性

`cell_config.c` / `cell_config.h` 在工作流之后被改过，journal 里引用的这两个文件的行号**可能失效**——本报告中涉及它们的行号已按当前磁盘版本复核修正。

其余 30 个 `.c`、32 个 `.h` 自工作流以来未变动（Glob 按 mtime 排序确认），journal 行号有效。
