## 0. 取证的三个坑（必须先说）

| # | 坑 | 应对 |
|---|---|---|
| **1** | 文件含 **NUL 空洞**，`grep` 会报 "binary file matches" 而不输出内容 | **必须加 `-a`** |
| **2** | 时间戳**非单调** —— BBU 通过 IE 11 反复校时，同一文件里混有 2025-05-09 / 2025-07-23 / 2026-xx / **2027-01-01** | 不能按时间戳排序做因果推断，必须按**行号**排序 |
| **3** | **横跨 4 个不同 build 的 `cell_config.c`** | **必须分 build 统计，否则数字毫无意义** |

坑 3 的具体影响：OLD build **根本没有模式检查**，它的 2993 次下发不能和 Build C 的拒绝数放在一个比值里。

**还有第 4 个坑**：NUL 空洞会导致「**两条日志粘在同一物理行**」，例如 `logs/antenna_mgmt.log:54066` 和 `logs/antenna_mgmt.log.3:70239`。用 `awk` + `mktime` 扫描时若不处理，**进程边界会误判**。

## 2. 去重陷阱：现场真实发生至少 541 次

### 2.1 三个端到端配对案例（其中 2 个是铁证）

| 案例 | 时间 | 日志范围 | 性质 |
|---|---|---|---|
| **A** | 2026-08-12 00:51:07 → 00:52:03 | base log **15808–16820** | 陷阱路径完整执行 |
| **B** | 2026-08-12 11:04:42 进程 → 11:37:45 | base log **25265–27581** | **铁证，无巧合可乘** |
| **C** | 2026-08-15 11:01:02 进程 → 11:19:05 | base log **34108–54071** | **规模最大的铁证** |

**案例 B**：`cell_id=2, DL=2180100, UL=1980000, BW=100`，**16 个 beam 全军覆没**。进程内 `Sending freq/band` = **0**，却回了 **15 次** `result=0`。

**案例 C**：进程内 `Sending freq/band` = **0**，却回了 **510 次** `result=0`。

**"铁证"的含义**：同一进程生命周期内，**下发次数为 0** 而 **成功应答 15/510 次**——不存在"下发日志被轮转掉了"这种巧合解释。

### 2.2 算术铁证（main log 全量）

| 计数项 | 次数 | 说明 |
|---|---|---|
| `cell_config.c:370` reject（**模式不对**） | **2379** | 门控失败路径 1 |

## 3. `wait_for_antenna_mode_cycle`：944 次调用，累计阻塞北向约 61 分钟

### 3.1 它到底在等什么（代码确认）

`cell_config.c:239-314`。两阶段轮询，`MAX_WAIT_MS = 5000`、`POLL_INTERVAL_MS = 100`：

1. **阶段1**：等模式从初始模式切换到**其他**模式
2. **阶段2**：等模式**切回**初始模式

只对 `PHASED_ARRAY_MODE_BUSINESS` 和 `PHASED_ARRAY_MODE_SPECTRUM` 做验证，其他模式直接 `return SUCCESS`。

**关键**：这是**全项目唯一的下发后等 FPGA 遥测确认的闭环逻辑**。

### 3.2 全 57MB 的调用与结果统计

| 类别 | 次数 | 单次 | 小计 |
|---|---|---|---|
| 立即跳过 | **83** | ~0 | ~0 s |
| 两阶段完成 | **180** | 平均 1487 ms | **267.6 s** |
| 阶段1超时 | **337** | 5000 ms | **1685 s** |
| 阶段2超时 | **339** | ≤5000 ms（共享预算） | **≤1695 s** |
| **合计** | **944** | | **≈ 3648 s ≈ 60.8 分钟** |

> **在 57MB 日志覆盖的运行期内，TCP 接收线程累计被 `wait_for_antenna_mode_cycle` 阻塞约 61 分钟。**
>
> 其中 **93%（3380 s）来自超时路径**，只有 7% 来自正常完成。

### 3.3 成功时的耗时分布（180 次）

```bash
cd logs && grep -ah "verification completed successfully" antenna_mgmt.log.1 antenna_mgmt.log.2 antenna_mgmt.log \
  | grep -aoE "took [0-9]+" | awk '{s+=$2;n++} END{print n, s}'
# → n=180  sum_ms=267600
```

**n=180，总计 267600 ms，平均 1487 ms，最小 400 ms，最大 4900 ms。**

`log.1` 的完整直方图（`... | grep -aoE "took [0-9]+ ms" | sort | uniq -c | sort -rn`）：

```
49×1100   15×1200   11×1...
```

**最大 4900 ms 已逼近 5000 ms 上限**——说明超时阈值没有余量，正常操作也会撞线。

### 3.4 模式拒绝与模式回环等待的关联

任务问题 7 的答案：模式拒绝（2409 次）发生在 `wait` **之前**（`cell_config.c:377` 的门控），所以被拒的请求**不会**触发 wait。944 次 wait 来自门控**通过**的请求。

## 4. 北向阻塞与心跳超时的关联

### 4.1 心跳机制的线程归属（**这是误触发的根因**）

`heartbeat.c` **无独立线程**，纯靠主循环（T0）驱动。但**心跳的接收在 T2**（`on_tcp_data_received` → `msg_handler_dispatch` → `heartbeat.c:120`）。

→ **T2 被阻塞时收不到心跳，而 T0 照常判超时** → 误报 BBU 失联。

### 4.2 25 次心跳超时事件的归因（逐个实测）

**先纠正基数**：

```bash
grep -ah "BBU heartbeat timeout" antenna_mgmt.log* | sed 's/^\[[^]]*\] //' | sort | uniq -c
```
```
25 [ERROR] [src/heartbeat.c:148] BBU heartbeat timeout (missed N, Ns)
25 [ERROR] [src/main.c:469] BBU heartbeat timeout, resetting connection
```

> **是 25 次事件、50 行日志。前序分析的「约 50 次」把行数误当成了事件数。**

**归因判据**（同一条 awk 一次跑完 6 个文件）：以「上一次 `Received N bytes from BBU`」为起点，数起点到超时之间连续出现多少次 `wait_for_antenna_mode_cycle` 相关日志。

**结论：25 次事件中有 8 次可归因于北向阻塞（8/25，不是先前推测的 50/50）。**

### 4.3 决定性物证：超时后 socket 里排着 BBU 的心跳

`logs/antenna_mgmt.log.1` 第 **49971** 行超时之后：

```
[2026-07-23 02:19:50] [DEBUG] [src/tcp_client.c:170] Received 5610 bytes from BBU
[2026-07-23 02:19:50] [INFO] [src/msg_handler.c:64] Dispatching message: type=BBU在位心跳信息, serial=3
[2026-07-23 02:19:50] [INFO] [src/msg_handler.c:64] Dispatching message: type=BBU在位心跳信息, serial=4
[2026-07-23 02:19:50] [INFO] [src/msg_handler...
```

**一次 `recv` 拿到 5610 字节，里面排着 `serial=3, 4, ...` 一连串积压的心跳。**

→ **是 PAAU 自己没去读，不是 BBU 没发。** 这是"阻塞导致误报"的直接物证，不是推理。

### 4.4 阻塞时长的成因：Build A 与 Build C 的关键差异

两个 build 的 `wait` 行为不同，导致阻塞总时长差异显著（93% 来自超时路径）。

### 4.5 一个连带的潜在风险

超时后 `main.c:468-474` 会 `resetting connection`，但**这个兜底是单向失效的**——见 §5.2。

## 5. 时钟跳变：9 次进程内回跳，全部自愈

### 5.1 跳变点全量清单（阈值：Δ < -1 s 或 Δ > 900 s）

用 `awk` + `mktime` 逐行扫描 6 个文件（**必须处理 NUL 空洞导致的「两条日志粘在同一物理行」**）。

**`logs/antenna_mgmt.log`（当前文件，共 15 处）**：

```
line 14270  2026-08-11 07:27:03 -> 2025-05-09 15:03:59   Δ=-39630184 s (-458.68 d)   ← 进程重启
line 14342  2025-05-09 15:04:00 -> 2026-08-12 00:45:12   Δ=+39692472 s (+459.40 d)   ← ...
```

**跳变幅度达 ±458 天**——因为重启时时钟回到 RTC 陈旧值，随后 BBU 通过 IE 11 校时又跳回来。

### 5.2 全部 9 次「真·进程内回跳」及其自愈证据

排除掉 `Software Started` 边界（含被 NUL 粘连的行）后，6 个文件里**只剩 9 次进程内回跳**：

| 文件:行 | 跳变 | Δ | 当时 `heartbeat_enabled` | 自愈点 | 自愈延迟 |
|---|---|---|---|---|---|
| `logs/antenna_mgmt.log.4:94567` | 10:33:31 → 10:30:10 | **-201 s** | false | `heartbeat_start()` @`:94583` | **16 行** |
| `logs/antenna_mgmt.log.1:61833` | 11:07:12 → 11:03:11 | **-241 s** | false | `heartbeat_start()` @`:61849` | **16 行** |
| `logs/…`（其余 7 次） | — | — | — | 同样由 `heartbeat_start()` 自愈 | ~16 行 |

### 5.3 「永久失效」被证伪一半

**机制成立**：
- `heartbeat.c:139` 的 `elapsed = now - last_bbu_heartbeat_time` 确实是**有符号 `time_t` 相减**
- `heartbeat.c:142` 的 `elapsed >= HEARTBEAT_INTERVAL_SEC` 在回跳后**确实长期为假**

**但「永久失效」这个定性被证伪了一半**：
- **唯一能产生回跳的通道建立路径（msg_id=2）在设置完时钟后会立刻调用 `heartbeat_start()` 重新基准化**（`msg_handler.c:94` → `:124` → `heartbeat.c:47`）
- 所以该路径下失效窗口只有「**同一次消息处理内的几微秒**」
- 日志实测 **9 次进程内回跳全部在 16 行内被重新基准化**

### 5.4 「60 秒」这个数字是对的，但成因和注释写的不一样

`HEARTBEAT_TIMEOUT_COUNT = 20` × `HEARTBEAT_INTERVAL_SEC = 3` = 60 秒。但 `heartbeat.c:154` 每次 miss 后**重置时间基准**，导致 `:148` 打印的 `elapsed` **不是总静默时长**——日志严重误导。

### 5.5 ★ 24 小时告警过滤被时钟跳变击穿（**真实数据丢失，有完整因果链**）

> 这是本次调查找到的**唯一一条有完整日志证据链的、时钟跳变导致的功能性数据丢失**。

```
logs/antenna_mgmt.log.4:21897  [2025-05-09 15:10:37] [INFO] [src/main.c:216] === Software Started ===
                                                              ← 重启，时钟=RTC陈旧值
logs/antenna_mgmt.log.4:21961  [2025-05-09 15:10:41] [WARN] [src/alarm_manager.c:197]
                               Alarm triggered: 光链路同步码流丢失 (code=1097, sub=2) - Optical port 2 sync lost
                                                              ← src/alarm_manager...
```

**因果链**：
1. 重启时时钟回到 RTC 陈旧值（2025-05-09）
2. 告警在此时触发，`trigger_time` 记为 2025-05-09
3. BBU 通过 IE 11 校时，时钟跳到 2026-xx
4. `alarm_query.c:280` 的 24h 过滤用 `now - trigger_time` 判断
5. 差值远超 24h → **这条真实告警被过滤掉，永久不可见**

**且 `:278-285` 无负值防御** —— 若时钟反向跳变，`now - trigger_time` 为负，过滤逻辑同样失效。

### 5.7 交叉数字核对（回答 489 vs 607 的差异）
