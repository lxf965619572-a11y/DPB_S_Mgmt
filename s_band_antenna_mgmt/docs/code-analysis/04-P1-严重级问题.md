# A. 固件上注链路不闭环

## A1. 上注结果从不回送 BBU，也不产生告警

`src/version_manager.c:1142` → 见 [03 §C2](03-P0-阻断级问题.md#c2-固件上注激活应答在上注启动之前发出)。

补充：`MSG_VERSION_UPDATE_RESULT_IND` 从未发出；`alarm_manager.c:487 alarm_trigger_version_*` 已预留但**未接线**。

---

## A2. `/dev/ttyAMA2` 打开失败时必然段错误

**代码事实**（`src/main.c:344-357`）：

```c
uart_rs422_open(...) 失败 → 只打 LOG_WARN("非致命错误,继续运行")
  → fpga_firmware_injection_init 被跳过
  → g_injection_task 保持全零（uart_client == NULL、state_mutex 未 init）
```

而 `src/version_manager.c:1156` 的 `fpga_firmware_injection_start` **不检查 init 是否执行过**。

**后果**：上注启动前不检查 `uart_client` 是否已初始化 → 解引用 NULL `uart_client` → **段错误**。

**触发条件**：`/dev/ttyAMA2` 不存在、被占用、或权限不足。这在现场是**完全可能**的（该串口是固件上注专用通道，与业务用的 `/dev/ttyAMA0` 分开）。

**修复**：`main.c:344` 失败时不要"继续运行"，或在 `fpga_firmware_injection_start` 入口检查 `uart_client != NULL && state_mutex 已 init`。

---

## A3. `progress_callback` 永远为 NULL —— 进度上报是结构性死代码

**代码事实**：
- `fpga_firmware_injector.h:65` 声明了回调字段
- `fpga_firmware_injector.c:666` 判空、`:685` 调用
- **整个工程（含 tests）没有任何一处给它赋值**，头文件也没有提供 setter API

同时 `fpga_firmware_injection_get_progress(:86)` / `_wait(:124)` / `_abort(:99)` 三个 API 在 `src/` 下**零调用者**。

**后果**：进度上报、等待完成、中止上注——三个能力都实现了，但**一个都不可达**。BBU 无法知道上注进行到哪一步，也无法中止。

---

## A4. 重构（reconfig）成功后不做任何业务恢复

**代码事实**（`src/fpga_firmware_injector.c:843-846`、`:255-270`）：`handle_reconfig_polling` 收到 `0x00` 后只做 `transition_state(COMPLETED)` 然后**线程退出**。

**机理**：FPGA 重构意味着**器件重新加载、内部寄存器与配置全部丢失**。但代码：
- 不重新下发小区配置 / 波束 / CPRI 模式 / 频点（`cell_config`、`channel_setup`、`fpga_handler` 均无调用）
- 不暂停 / 恢复喂狗
- 不暂停 / 恢复状态轮询

**后果**：固件上注成功后，**天线回到全零配置状态**，而 PAAU 的本地状态表（`g_cell_mgr`）仍认为频点都配着。北向查询会返回与硬件完全不符的数据。

> 这是 [02 §5.1](02-方法与数据来源.md) 提到的 `e2e-flow` 缺口的典型体现：**跨子系统的时序影响没有独立 agent 核查过**。上注期间业务面会怎样，只有零散提及（"不停业务、不关闭小区、不通知 FPGA 进入维护态、不暂停 1s 状态轮询、不暂停 3s 喂狗"），没有完整时序推演。

---

## A5. cleanup 在 detached 线程可能仍在运行时销毁 mutex

**代码事实**（`src/fpga_firmware_injector.c`）：
- `:78` 线程是 `pthread_detach` 的
- `:155` cleanup 只 `sleep(2)`
- `:166` 就 `pthread_mutex_destroy`

而线程内部单次阻塞可达：
- `:448` `sleep(20)`（注释"子阵擦除完成要等待20s"）
- TRANSFER_START 轮询 **300s**
- 重构轮询 **600s**

**后果**：`sleep(2)` 远小于线程可能的运行时长 → cleanup 销毁 mutex、`fclose` 线程正在读的 `FILE*`、随后 `close` 线程正在写的 fd → **use-after-free / use-after-close**。

**叠加**（P2）：`start()` 不重置上一次的传输游标，两次上注之间 `get_progress` 会返回**陈旧数据**。

---

## A6. `send_transfer_abort` 把同一个 3-9 中止帧在线上发了两遍

**代码事实**（`src/fpga_firmware_injector.c`）：
```c
:474   uart_rs422_send_frame(abort_frame);           /* 第一遍 */
:483   uart_rs422_send_and_wait(abort_frame, ...);   /* 内部第一步就是 uart_rs422_send_frame（uart_rs422_client.c:444）→ 第二遍 */
```

**后果**：FPGA 会收到**两条 3-9**，可能回**两条 3-10**，而接收侧只等一条 → 第二条应答残留在环形缓冲里，**串到下一次交互**。

---

## A7. `handle_transfer_start` 无条件 `sleep(20)`，且不可中止

**代码事实**（`src/fpga_firmware_injector.c:448`）：`sleep(20)` 带注释"子阵擦除完成要等待20s，擦除其他子阵"，但它位于 **FPGA 已明确回答 READY(0x00) 之后**——即无条件等待，不看 FPGA 是否真的需要。

**叠加**：这段与整个 **300s 轮询循环都不可中止**（`abort_requested` 在循环内不被检查）。

**后果**：一次上注的最坏耗时被这 20 秒无条件抬高；`_abort()` API 即使被接线也无法中止。

# B. 版本管理

## B1. 用官方脚本打的固件包，激活必然失败

**代码事实**：
- `src/version_manager.c:1125` 固件激活路径调 `load_version_metadata()`
- 该函数只找 `metadata.txt` 或 `version.json`
- 而仓库自带的 `scripts/create_version_package.sh:99-109` 打出的包里**只有 `antenna_mgmt.bin` 和 `checksum.txt`，没有 `metadata.txt`**

**后果**：用官方脚本打的固件包，`:1125` **必然失败** → `result = ACTIVATE_RESULT_CORRUPTED(2)` → **固件永远无法激活**。

> 这是"文档 vs 代码 vs 脚本"三方不一致的典型案例。按 `docs/VERSION_MANAGEMENT.md` 的包规范操作会得到一个激活不了的包。

**相关**（P2）：`read_checksum_from_txt`（`:128`）用 `readdir` 找「**第一个** `.txt` 结尾的文件」作为校验和来源，**不认文件名**。`readdir` 顺序由文件系统决定，不保证。若版本目录里同时有 `metadata.txt` 和 `checksum.txt`（文档的包规范就有 `metadata.txt`），可能读错文件。

---

## B2. 软件激活的重启方式有三处问题

**代码事实**（`src/version_manager.c:1179`）：

```c
system("systemctl restart antenna-mgmt.service &");   /* 在消息处理线程里 */
:1176   sleep(3);                                      /* 同步睡 */
:1167   写标记文件 /tmp/antenna_mgmt_restart_pending
```

三个问题：

1. **`PrivateTmp=true`**（`scripts/antenna-mgmt.service:35`）意味着这个 `/tmp` 是**服务私有挂载**，标记文件写在私有命名空间里，外部脚本看不到
2. **标记文件无人读取**——`grep antenna_mgmt_restart_pending` 全仓库只命中 `src/version_manager.c:1167` 这一处
3. **自杀式重启与北向处理耦合在同一线程**——`version_manager` 在 recv 线程里通过 `system()` 重启自己所在的 systemd 服务

**修复方向**：dispatch 只入队，业务在独立工作线程执行。

---

## B3. 下载线程无磁盘空间检查

`src/version_manager.c:968`：`DOWNLOAD_ACK_REJECT_SPACE(=2)` 在 `include/version_manager.h:21` 定义，**全项目 grep 无使用点**；也没有 `statvfs` / `df` 调用。

`docs/VERSION_MANAGEMENT.md:193` 写「升级前确保有足够的磁盘空间（至少 100MB）」——**这是对人说的，不是代码做的**。

**后果**：磁盘满时下载/解压失败，错误路径混乱；且失败路径不删 tar 包（见 P3）。

---

## B4. 符号链接切换不是原子的

**代码事实**（`src/version_manager.c`）：
```c
:911   unlink("/opt/vendor/current");
:914   symlink(...);        /* 注释（:846）却写着「原子操作」 */
```

**机理**：两步之间 `/opt/vendor/current` **不存在**。

**后果**：若此刻 systemd 因 `Restart=always` 拉起服务，launcher 脚本找不到 `current` → 启动失败。

**正确做法**：`symlink` 到临时名 + `rename`（rename 在同一文件系统内是原子的）。

# C. RS-422 / pkfinder 传输层

## C1. 跨多次 `read()` 到达的帧永远收不完整

这是**上注失败的头号嫌疑**，两处同源缺陷：

### C1a. `pkfinderParse` 把「数据还没收全」当成致命错误

**代码事实**（`src/pkfinder.c`）：
- `:152` `pk_fres` 初始化为 `ERROR(-1)`
- 只有在 `chkExec` 返回 `TRUE`（找到并校验通过一个完整包）时才在 `:189` 置 `OK(0)`
- 因此「没找到包头」（`:167-171` break）和「找到包头但长度不足」（`:172-183` break）这两个**最常见的中间状态**都会返回 `ERROR`

**调用方误用**（`src/uart_rs422_client.c:419`）：
```c
else if (status == ERROR) { /* 立即失败 */ }
```

**后果**：任何跨两次 `read` 到达的应答帧都会以 `ERROR_GENERAL` 失败。

> ⚠️ **未闭合问题**：`pkfinder` 是**移植件**（从推测为航空/1553 总线的项目移植进来），原作者（xumd，513 所）可能有别的用法约定。需要确认原项目里 `pkfinderParse` 的调用方是怎么处理返回值的——`uart_rs422_client.c:419` 那种「ERROR 就立即失败」的写法**很可能就是误用**。

### C1b. 包头扫描循环上界无符号下溢 → 大范围越界读

**代码事实**（`src/pkfinder.c:60`）：
```c
for (i = 0; i < (len - pkfndr->headLen + 1); i++)   /* len、headLen 都是 UINT */
```

**机理**：`len=0` / `headLen=2` 时表达式 = `0xFFFFFFFF`，循环会一路读 `buf[i+j]` **直到段错误**。

**当前缓解**：唯一调用路径 `pkfinderParse` 用 `while ((fndIndex+pkfndr->headLen)<=datLen)`（`:164`）挡住了。但这是**巧合安全**——任何新增调用方都会踩雷。

---

## C2. `pkfinderFind` 定长包分支不写 `*fndLen`

**代码事实**（`src/pkfinder.c:84-87`）：定长包长度不够时 `return 1` 而**没有给 `*fndLen` 赋值**（变长分支 `:130` 有赋值）。

**后果**：调用方 `pkfinderParse` 的 `:174 if (pkLen>parseBufLen)` 读的就是这个**未初始化/过期的 `pkLen`**——`pkLen` 在 `:148` 初始化为 0，但在 while 循环的**第二轮及以后**会带着上一轮的残值做判断。

**同类**（P3）：`:101-104`（变长包连长度域都取不出来）也有两条 `return 1` 路径不给 `*fndLen` 赋值。

---

## C3. `rs422_decode_frame` 的 `payload_len` 无符号下溢

**代码事实**（`src/rs422_protocol.c`）：
```c
:173   actual_data_len = data_len + 1;
:174   长度校验只要求 frame_len >= 8 + actual_data_len
:204   uint32_t pl_len = actual_data_len - 2;    /* ← 之前没有判 actual_data_len >= 2 */
```

**机理**：`data_len` 字段为 0 或 1 时，返回 `0xFFFFFFFE` / `0xFFFFFFFF`。

**后果**：**下游所有长度校验失效**。应答帧的"数据域长度"为 0 或 1 时即可触发。

---

## C4. 8O1 奇校验模式下清掉 `INPCK`

**代码事实**（`src/uart_rs422_client.c`）：
- `:190-191` 置了 `PARENB|PARODD`，使**发送侧**产生奇校验位（这是 FPGA 需要的位计数）
- `:216` `options.c_iflag &= ~(INPCK | ISTRIP)` —— **关闭了驱动的输入校验检查**

**后果**：接收端**完全不检查校验位**，RS-422 链路上**唯一的物理层纠错能力被关闭**。

**对比**：北向 133 字节遥测帧也完全无校验（见 D2），两条链路的完整性保障都缺失。

---

## C5. 发送重试从帧头整帧重写，不从短写偏移续写

**代码事实**（`src/uart_rs422_client.c`）：
- `:167` open 用了 `O_NDELAY`，此后**从未 `fcntl` 清除** → fd 是非阻塞的
- 1012 字节的数据帧在 921600 波特下需要约 **11ms** 才能发完
- `:280` 只在短写时**从帧头整帧重写**

**后果**：驱动 TX 缓冲不足时 `write` 会短写，整帧重写会在链路上产生**重复字节** → FPGA 侧帧解析错乱。

---

## C6. 一次 `pkfinderParse` 里到达多个完整帧时，前面的帧被静默丢弃

**代码事实**（`src/uart_rs422_client.c:81-83`）：`rs422_frame_check_and_process` 每被回调一次就**无条件 memcpy 覆盖** `g_recv_ctx.received_frame` 并置 `frame_ready=1`。

**机理**：而 `pkfinderParse` 一次可以解析出**多个**完整包，逐个回调。

**后果**：只把**最后一帧**交给上层，前面的帧全部丢失。

**相关**（P2）：接收环形缓冲与 pkfinder 状态**跨包不清零**（`:323` 进入时只清 `frame_ready`，不清 `g_recv_ctx.rbuf` 也不复位 pkfinder）→ 超时后的**迟到应答会串到下一包**。injector 侧的 `tcflush(fd, TCIOFLUSH)` 只清内核缓冲，清不掉应用层环形缓冲。

# D. FPGA 南向通信

## D1. `fpga_handler_get_status` 不判新鲜度 —— FPGA 掉线后永久上报陈旧遥测

**代码事实**（`src/fpga_handler.c`）：
- `:40` `status_valid` **一旦置 true 就永远不会回退**
- `:41` `last_update_time` 被写入，但 **grep 确认全项目没有任何地方读取它**
- `:73` `get_status` 只判「是否曾收到过一帧」

**叠加**：`uart_poll_thread` 发送失败（`src/uart_client.c:320`）只打一条 `ERROR`，**没有连续失败计数、没有超时判定、不触发告警**。

**后果**：FPGA 掉线（串口拔了、FPGA 挂了、线缆故障）后，北向会**永久上报最后一次收到的陈旧遥测**，且**不产生任何告警**。BBU 看到的是"一切正常"的假象。

> 这与 C4（去重陷阱的第二条触发路径：遥测不可用）叠加，会让故障更难被发现。

---

## D2. 133 字节遥测帧完全没有校验和 / CRC

**代码事实**（`include/fpga_protocol.h:145`）：对全部 5 个 `.c` 和 5 个 `.h` grep「`crc|checksum|cksum|escape`」**零命中**。

帧完整性只靠 `0xEB90` 帧头和 `0x5555` 帧尾**两个魔数**（`src/uart_client.c:171`、`:221`）。

**后果**：921600 波特**无流控**的 UART 上，载荷内部**任意一位翻转**都会被当作合法遥测接受 → 污染 `g_fpga_state` → 被 `status_query` / `param_query` / `channel_setup` / `cell_config` / `alarm_manager` 全部下游消费。

**对比**：RS-422 上注链路**有** CRC16-CCITT-FALSE。同项目两条串口链路，一条有校验一条没有。

---

## D3. 帧头搜索循环在 `remaining==1` 时丢弃最后一个字节

**代码事实**（`src/uart_client.c:167`）：
```c
for (header_pos = 0; header_pos < remaining - 1; header_pos++)   /* remaining 是 uint32_t */
```

**机理**：当缓冲区里只剩 1 个字节时，`remaining - 1 == 0`，for 循环体**一次都不执行** → `found_header = false` → `:179 processed_bytes = frame_offset;` 把这唯一字节**无条件丢弃**。

**后果**：破坏**跨 read 分割的帧头**。若 `0xEB` 和 `0x90` 分两次 read 到达（921600 波特下完全可能），`0xEB` 被丢掉，整帧丢失。

---

## D4. 整个 `fpga_to_cpri.c` 是死代码，且内部有硬编码假数据

**代码事实**（`src/fpga_to_cpri.c:80`）：grep 确认三个导出函数（`fpga_to_cpri_status_response` / `_param_response` / `_alarm_report`）除自身声明和定义外**零调用者**，但 `Makefile:18` 的 wildcard 仍把它**编进 antenna_mgmt**。

文件内部：`:80 uint32_t beam_status = 0; /* 从fpga_s... */`（硬编码假数据）+ 占位告警码。

**二进制取证确认**：42 个死代码符号**全部存在，无一被 gc 掉**；`.dynsym` 只导出 2 个已定义符号。死代码体积已核算（文件总 692104 字节）。

**附带**（P3）：`add_ie_to_payload` 溢出时返回错误但调用方**全部忽略**（`:82`、`:91`、`:95`、`:99`、`:103`、`:140`、`:147`、`:150`、`:153`、`:156`、`:240` 共 **11 处**），且 payload 指针/offset 状态不一致。

---

## D5. 接收线程节奏撑爆内核 tty 缓冲

**代码事实**（`src/uart_client.c:284`）：接收线程每轮固定 `usleep(10ms)` + **每条日志两次 `fflush`**。

**算术**：
- 921600 bps ≈ 92160 字节/秒 ≈ **921 字节/10ms**
- `read` 缓冲只有 **1024 字节**（`:125`）
- 重组缓冲 **2048 字节**（`:126`）

**后果**：余量只有 100 字节。任何调度延迟（`fflush` 的阻塞文件 I/O、系统负载）都会让内核 tty 缓冲溢出 → **丢字节** → 帧解析错乱。

# E. 管理面业务

## E1. 用线上的 `msg_length` 而非实际 `payload_len` 计算解析范围

**代码事实**（`src/param_config.c:163`）：
```c
payload_len = request->header.msg_length - sizeof(cpri_msg_header_t);
```
`msg_length` **直接来自报文**（`cpri_protocol.c:167`）。

**缓解不足**：`main.c:123` 只校验 `msg_length` 在 15~8192 之间，而 `cpri_decode_message:178` 发现 `msg_length` 与实收长度不符时**只打日志不拒绝**。

**后果**：**可越界读**。攻击者（或故障的 BBU）声明一个大 `msg_length` 但只发少量字节，解析会读到缓冲区之外。

## E2. 跨解锁窗口持有记录指针，`reported` 标志可能打到错误的告警上

**代码事实**（`src/alarm_manager.c`）：
```c
:364   pthread_mutex_unlock(...);
       alarm_report_to_bbu(...)      /* 内部含 tcp_client_send，可能长时间阻塞 */
:369   pthread_mutex_lock(...);
:372   record->reported = true;      /* ← record 指向共享的 records[] 槽位 */
```

**机理**：解锁窗口内另一线程（UART recv 线程每秒都在跑 `alarm_periodic_check`）可能已经 `alarm_clear` 并让 `find_free_record` **复用了这个槽位**。

**后果**：`reported = true` 打到了**另一条告警**上。

**加重因素**：`alarm_clear`（`:255`）置 `active=false` 后槽位**立刻被复用**，`clear_time`（`:243`）写了也无人读——**无告警历史，清除即销毁**。

## E3. CPRI 工作模式的取值语义三方整体差 1

**代码事实**：

| 来源 | 声明 |
|---|---|
| `src/param_config.h:30` | IE 字段：`1:普通 2:级联 3:主备 4:负荷分担` |
| `include/fpga_protocol.h:97` | FPGA 侧 `cpri_work_mode`：`1=普通，2=级联，3=主备，4=反向分担` |
| `src/param_config.c:128-134` | 校验只拒绝 `>3` 的值，接受 **0~3** 并**原样下发** FPGA（→ `fpga_handler.c:377` / `:112`） |

**后果**：代码接受 0~3，两份文档都说 1~4。**整体差 1**。BBU 发 `1`（普通）→ PAAU 原样下发 `1` → FPGA 按自己的表解释。若 FPGA 实际是 0 基，所有模式都错位一档。

> 协议一致性调查的结论：**「线上实证走的是无校验的那条路」**——即实际部署中这个字段没有被严格约束过，所以矛盾一直没暴露。

**这是必须向硬件方确认的问题之一**，见 [09-协议一致性](09-协议一致性.md)。

## G2. `rs422_decode_frame` 只接受 `0x1ACF`，而 encode 只产生 `0xEB90`

**代码事实**（`src/rs422_protocol.c`）：
- `:89` 写入 `htons(RS422_SYNC_WORD_CMD)` = `0xEB90`
- `:149` 判断 `if (sync != RS422_SYNC_WORD_ACK)`（`0x1ACF`，`:8`）就 `LOG_ERROR` 返回 `ERROR_GENERAL`

**后果**：`test_rs422_protocol.cpp` 的 **5 个编解码往返单元测试必然失败**。

> 这本身可能是**正确设计**（命令用 `0xEB90`、应答用 `0x1ACF`，两个同步字区分方向），但**测试写的是往返**（encode 后 decode），所以测试的假设错了。需要确认到底哪边对。

**Mock 侧同源问题**（P2）：Mock 应答**用错同步字** → **25+ 个用例必然失败**。
