## C. 确认的竞态 / UB，按严重程度排序

### C-1【严重】退出路径：3 个 detached 线程 + `logger_close()` 无锁 + `pthread_mutex_destroy` 在用锁 → use-after-free

**证据链**：
- `src/log_upload.c:351`、`src/version_manager.c:1072`、`src/fpga_firmware_injector.c:78` 三处 `pthread_detach`，**无任何 join 手段**
- `src/log_upload.c:357-367` `log_upload_destroy()` 只在发现 `g_upload_in_progress` 时打一行 `LOG_WARN`，**不等待、不销毁 `g_upload_mutex`**。`src/version_manager.c:1250-1259` **同构**
- `src/fpga_firmware_injector.c:146-169` cleanup 只 `sleep(2)` 就 `pthread_mutex_destroy`（`:166`），而线程内部单次阻塞可达 20s / 300s / 600s
- `logger_close()` **完全不加 `g_log_mutex`**，而全部 9 个执行流都在写 `g_log_file`

**后果**：`main.c:481-514` 的 cleanup 序列销毁 mutex 和 logger 时，detached 线程可能仍在使用它们。

---

### C-2【严重】TCP 停止序列：`recv_thread` tid 无同步被覆写，T2 可在 `state_mutex` 被销毁后仍使用它，且旧 recv 线程永不 join

**证据链**：
- `src/tcp_client.c:123` `pthread_create(&client->recv_thread, ...)` 由 **T1** 执行
- `src/tcp_client.c:272` `if (client->recv_thread) pthread_join(...)` 由 **T0** 执行
- **两者对同一个 `pthread_t` 字段无任何同步**（不在 `state_mutex` 内）

**时序**：T0 `tcp_client_stop:261` 置 `running=false` → T1 已经越过 `:143` 的循环判断、正阻塞在 `tcp_connect_to_server:91` 的 5 秒 select 里 → select 超时返回后 T1 继续执行 `:123` **覆写 tid** → 旧 T2 的 tid **永久丢失，永不 join**。

---

### C-3【严重】`version_manager` 的 `in_progress` 闸门被自己的 memset 打掉，可并发两个下载线程操作同一全局与同一目录

**证据链**：
```
src/version_manager.c:968-978   持 g_download_mutex 检查并置 in_progress = true
                        :978    解锁
                        :987    memset(&g_download_task, 0, sizeof(...))  ← 在锁外，把刚置的 true 抹回 false
                        ...     （含多次 strncpy、strstr、两次 config_get_*）
                       :1040    才在锁外重新置 true
```

**窗口**：`:987`–`:1040` 之间，第二个 MsgID 21 到达时 `:969` 的检查**通过** → 并发两个下载线程操作同一全局与同一目录。

---

### C-4【严重】`tcp_client_send` 无发送互斥，5 个线程可在同一 socket 上交织字节流；且 sockfd 快照后解锁 → fd 复用写入错误目标

**证据链**：
- `include/tcp_client.h:15-28` 的 `tcp_client_t` 里**只有 `state_mutex`，没有 `send_mutex`**
  - 对比：`include/uart_client.h:27` **有** `send_mutex`；`include/uart_rs422_client.h:20-21` **有** `send_mutex` + `recv_mutex`
  - → 说明这是**遗漏**，不是设计
- `src/tcp_client.c:218-226` 持锁**只为取 `sockfd` 快照**，`:226` 解锁
- `:229-236` 的 `while(sent<len) send(...)` 循环**完全在锁外**
- 并发发送方：**5 个线程**（已用 grep 穷举确认）

**后果**：
1. 5 个线程可在同一 socket 上**交织字节流** → BBU 侧解析错乱
2. sockfd 快照后解锁 → **fd 复用写入错误目标**

---

### C-5【严重】二次 `pthread_join` 同一 tid（TCP 与 UART 各一处），日志实证

**TCP 侧**：
```
main.c:495   tcp_client_stop()   → tcp_client.c:273/276   两个 join
main.c:496   tcp_client_destroy() → tcp_client.c:289      再调一次 tcp_client_stop → 同样两个 join 跑第二遍
```
`tcp_client.c:273/276` 之后**没有把 tid 清零**，所以 `if (client->recv_thread)` 的保护**恒真**。

**UART 侧**：
```
main.c:497   uart_client_close()   → uart_client.c:386/389   join
main.c:498   uart_client_destroy() →                          再 join 一次
```
同样**不清零 tid**。

**已有日志实证**（不是纯推理）。

---

### C-6【严重】signal handler 内 async-signal-unsafe 调用，会在 `g_log_mutex` 上自死锁

**证据链**：
```c
src/main.c:54    LOG_INFO("Received signal %d, shutting down...")
                   → src/logger.c:181  logger_log
                       :201  pthread_mutex_lock(&g_log_mutex)     ← async-signal-unsafe
                       :193  localtime                            ← async-signal-unsafe
                       :211/:216  fprintf                         ← async-signal-unsafe
                       :212/:218  fflush                          ← async-signal-unsafe
src/main.c:55    g_running = false;      ← 在 LOG_INFO 之后！
```

**全部不在 POSIX async-signal-safe 列表里。**

**关键**：`g_running = false` 在 `main.c:55`，即**在 LOG_INFO 之后**。若 handler 死锁在 `:201`，**`g_running` 永远不会被置 false** → 进程无法退出，只能 `kill -9`。

**这是本项目唯一可确认的死锁路径**，且有 **2 条日志旁证**。

`g_log_mutex` 是普通（**非递归、非 robust**）互斥锁，handler 在被中断线程持锁时再次 `pthread_mutex_lock` → **永久阻塞**。

### C-7【严重】`fpga_watchdog_destroy` 与 init 失败路径：destroy 未初始化的 mutex / 二次 destroy

**证据链**：
```
src/fpga_watchdog.c:371-375   watchdog_gpio_init 失败时
                       :373   已 pthread_mutex_destroy(&g_watchdog_mgr.mutex) 后 return ERROR_GENERAL
src/main.c:389-391            只 LOG_WARN 后继续
src/main.c:486                无条件 fpga_watchdog_destroy()
                       :456   第二次 pthread_mutex_destroy 同一个 mutex → UB
```

更早的 `goto cleanup`（`src/main.c:224/231/238/…`）路径同样。

**另**：`fpga_watchdog_destroy:436` **不检查 `enabled` 也不 join 喂狗线程**就 munmap（`:439-448`）→ 若 stop 未被调用，喂狗线程会在 3 秒后访问**已 unmap 的内存** → 段错误（use-after-unmap）。

### C-8【中】`alarm_manager` 跨解锁窗口使用记录指针/索引，`reported` 标志会打到错误的告警上

```
src/alarm_manager.c:364   pthread_mutex_unlock(...)
                          alarm_report_to_bbu(...)   ← 内部含 tcp_client_send，可能长时间阻塞
                  :369   pthread_mutex_lock(...)
                  :372   record->reported = true      ← record 指向共享的 records[] 槽位
```

解锁窗口内另一线程（**UART recv 线程 T3 每秒都在跑 `alarm_periodic_check`**）可能已经 `alarm_clear` 并让 `find_free_record(:142)` **复用了这个槽位**。

**加重**：`alarm_clear(:255)` 置 `active=false` 后槽位**立刻被复用**，`clear_time(:243)` 写了也无人读 → **无告警历史**。

### C-9【中】`g_channel_established` 四线程无锁读写 + T2 尾部回调可覆盖 T1 刚建立的新连接状态

**写点**：`main.c:147`(T2)、`main.c:95`(T2，在 `on_tcp_disconnected` 里)、**`main.c:65`(T1，在 `on_tcp_connected` 里)**、`main.c:471`(T0)
**读点**：`main.c:436`/`:461`(T0)

`volatile bool` **不提供 C 内存模型下的原子性与顺序保证**；AArch64 上字节存取实践中原子，故属**低危数据竞争**。

**真正的逻辑竞态**（**修正摘要**，见 [02 §3 自我纠错](02-方法与数据来源.md#3-自我纠错工作流内部的证伪)）：T2 在 `tcp_client.c:198` 释放 `state_mutex` 后才调 `on_tcp_disconnected` → 该回调可以在 T1 已经建立**新连接**之后执行，把 `g_channel_established` 覆写回 false。

---

### C-10【中】`tcp_client_stop` 与 `tcp_connect_to_server` 的竞争可在 cleanup 期间新建连接

`tcp_client.c:261` `running=false` **只在 T1 的 `:143` 循环顶部被检查**。若 T1 此刻已在 `tcp_connect_to_server` 内部（阻塞在 `:91` 的 5 秒 select），它会在 stop 之后**继续执行**：

```
:111-114   写 sockfd/state
:119-120   告警
:123       新建 T2'
:132       on_connected → main.c:69 channel_setup_create_request → main.c:82 tcp_client_send
```

→ **在 cleanup 期间新建连接并发送数据**。

### C-11【中】`uart_client_close` 先 close(fd) 再 join；`uart_client_send` 的状态检查在锁外

```
src/uart_client.c:376   置 running=false
                :378-381   立即 close(client->fd); client->fd = -1;
                :382       state=CLOSED
                :385-390   才 join
```

T3 可能正阻塞在 `:137 read(client->fd, ...)`；`client->fd` 被 T0 **无锁改写**为 -1 → T3 `read(-1)` → EBADF → `:279-281` 打日志 break。

**勉强安全**，但对 `client->fd`（普通 int）的并发读写本身是**数据竞争**。

### C-13【中】`g_log_mutex` 临界区覆盖阻塞文件 I/O，是全局串行化点，也放大 C-6 的死锁窗口

`src/logger.c:201-221` 锁内做：

### C-14【低】`tcp_recv_thread` 可能读取未初始化的 `ret`

- `src/tcp_client.c:165` `int ret;` **无初值**
- `:167` 的 `while (client->running)` 若在 T0 于 `:261` 置 false **之后**才第一次求值，循环体**一次都不执行**

**加重**：`Makefile:5` 开了 `-Wall -Wextra`，`-Wmaybe-uninitialized` **应当报警，说明告警被忽略**。日志中 **487 条** `Recv thread exiting`。

## D. 死锁分析

### D.1 锁序图（实测归纳，全部单向）

```
g_cell_mgr.mutex ──> g_fpga_state.status_mutex      (cell_config.c:325 → :361)
g_cell_mgr.mutex ──> uart send_mutex                (cell_config.c:131/:325 → :207/:495/:525/:530/:545 → uart_client.c:340)
g_cell_mgr.mutex ──> g_log_mutex                    (cell_config.c 锁内大量 LOG_*)
rs422 recv_mutex ──> g_log_mutex                    (uart_rs422_client.c:320 → :397 → pkfinder 回调)
```

**全部单向 → 无锁序环。**

### D.2 真实存在的死锁只有一处：信号处理器自死锁

见 **C-6**。这是本项目**唯一可确认的死锁路径**，且有 **2 条日志旁证**。

### D.3 持锁阻塞（非死锁，但会造成长时间锁占用）

> **这一节直接对应项目已保存的认知：CPRI 接收循环是单线程的，handler 里任何阻塞都会拖死整条 BBU 链路。**

| 位置 | 阻塞内容 | 时长量级 |
|---|---|---|
| `src/logger.c:201-221` | 全局锁内做 4 次 stdio + 可能的 `stat`/`rename`/`unlink`/`fopen` | **9 个执行流全部串行化** |
| `src/cell_config.c:325` → `:495` → `uart_client.c:340-356` | `g_cell_mgr.mutex` 内做**阻塞 `write()` 循环 + `tcdrain()`** | 921600 波特下**等物理发完** |
| `src/uart_rs422_client.c:320` → `:361` | `recv_mutex` 内做最长 `client->timeout_ms`（默认 **5000ms**，`:16`/`:142`）的 `select` | **T6 每次问答都持锁 5 秒量级** |
| `src/cell_config.c:510` `wait_for_antenna_mode_cycle` | 在 **TCP recv 线程（T2）** 上阻塞 | **最长 5 秒**（实测平均 1.49 秒） |
| `src/reset.c:253` / `:271` | `sleep(2)` 在消息处理线程里 | 2 秒 |
| `src/version_manager.c:1176` | `sleep(3)` 在消息处理线程里 | 3 秒 |

**后果**：T2 被阻塞期间**不读 socket** → BBU 的心跳积压在内核缓冲 → `heartbeat_check_timeout` 判超时 → **误报 BBU 失联**。

日志实证：**25 次心跳超时事件中 8 次可归因于此**。决定性物证见 [11 §6.4](11-现场日志实证.md)。

**修复**（P1-2）：把 `cell_config.c:239-314` 的阻塞等待移出 TCP recv 线程。

### D.4 漏解锁核查（专项，逐个函数核对）

**已完成逐函数 lock/unlock 配平核查。结论：无漏解锁。**

唯一需要注意的是 `cell_config.c:507`/`:516`/`:522` 的**主动放锁-重加锁**模式——代码里有明确注释「重新加锁以保持函数退出时的锁状态一致」，配平正确，但这个模式本身制造了 C-8 类型的跨解锁窗口风险。

### D.5 回调重入核查（专项）

已核查。关键发现：**`on_tcp_disconnected`（T2）可以在 T1 已建立新连接之后执行**（C-9 的逻辑竞态）。
