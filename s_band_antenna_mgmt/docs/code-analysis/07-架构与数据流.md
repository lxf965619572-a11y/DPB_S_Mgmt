## 1. 系统定位

这是 **PAAU 侧**（相控阵天线管理单元）的管理面软件，进程名 `antenna_mgmt`。它夹在两个方向之间：

```
        北向（TCP，小端，类 CPRI 协议）
   BBU ─────────────────────────────────► PAAU (antenna_mgmt)
   10.10.10.6                              飞腾 D2000 / AArch64
                                                │
                                                ├── /dev/ttyAMA0  921600-8N1  大端  业务通道
                                                │     0xEB90 帧头 + msg_id + length + payload + 0x5555 帧尾
                                                │
                                                └── /dev/ttyAMA2  921600-8O1  RS-422  固件上注专用
                                                      CCSDS 风格帧（QNIXY32110-2023 规范）
                                                      
                                                + /dev/mem mmap → IOMUX(0x28180214) / GPIO0(0x28004000)
                                                  独立线程每 3 秒翻转 GPIO0_B6 喂硬件看门狗
```

**18 个业务模块 + 2 路 UART + TCP 客户端 + GPIO 看门狗**，由 `main()` 按固定顺序拉起。

## 2. 消息头与 IE 布局

### 2.1 北向 CPRI 消息头（15 字节，packed）

`include/cpri_protocol.h:48-55`，编码在 `src/cpri_protocol.c:115-152`：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | `msg_id` | 消息类型（34 个已命名） |
| 4 | 4 | `msg_length` | **含头部**，即 `15 + payload_len` |
| 8 | 1 | `paau_id` | ⚠️ **无一处参与判断** |
| 9 | 1 | `bbu_id` | ⚠️ **无一处参与判断** |
| 10 | 1 | `port_num` | 光纤端口号。⚠️ **纯装饰字段，且存在两套互不关联的语义** |
| 11 | 4 | `serial_num` | 流水号。出站递增，**入站零校验** |

`4+4+1+1+1+4 = 15` 字节。

`main.c:118-120` 直接 memcpy 偏移 4 读长度做粘包切分，注释明说「**D2000 CPU是小端序，直接读取**」，不做任何字节序转换。

### 2.2 IE（TLV）头（4 字节）

`include/cpri_protocol.h:58-61`：`ie_type`(2) + `ie_length`(2)。

**`ie_length` 含 IE 头**（四源一致）。但**下界校验系统性缺失**——6 处 TLV 循环里只有 1 处有 `ie_len < 4` 检查，见 [03 §B1](03-P0-阻断级问题.md#b1-tlv-下界校验缺失--接收线程死循环)。

**IE 编号无统一注册表，存在三处撞号**，其中 **IE 14 撞号成立**（两处布局完全一致）。

### 2.3 南向 FPGA UART 协议（`/dev/ttyAMA0`，921600-8N1，大端序）

**下行命令帧**（`fpga_protocol.h:8-14`，`fpga_encode_message`）：

```
帧头 0xEB90(2, 大端) + msg_id(1) + length(1) + payload(N) + 帧尾 0x5555(2, 大端)
```

⚠️ **`length` 字段语义三者互不一致**：
- `fpga_protocol.c:98` 注释：「包含 msg_id(1) + length 本身(1) + 数据(N)」，即 `length = N + 2`
- `fpga_protocol.c:99` 代码：`length_field = msg->payload_len`，即 `length = N`
- `fpga_protocol.c:167` 解码：`payload_len = (length_field >= 2) ? length_field - 2 : 0`，即 `length = N + 2`

→ **`encode(decode(x)) != x`**。日志实证：旧构建发 `length=2`（N+2 语义），当前发 `length=1`（N 语义），**FPGA 两版都接受** → **无法判定哪个符合规范**（无 ICD）。

**上行状态帧固定 133 字节**：

```
帧头 0xEB90(2) + length(2, 大端, 值=127) + 数据(127) + 帧尾 0x5555(2)
```

**没有 msg_id 字段**（`fpga_protocol.h:141-144` 特别注明）。

⚠️ **完全无校验和/CRC**：对全部 5 个 `.c` 和 5 个 `.h` grep「`crc|checksum|cksum|escape`」**零命中**。完整性只靠两个魔数。

### 2.4 字节序：三套约定并存，零条件编译

| 约定 | 用在哪 |
|---|---|
| 直接 memcpy，假定小端主机 | CPRI 侧绝大部分字段（`cell_config.c:73-113`、`transparent_msg.c:360-374`、`cpri_protocol.c:129-141`） |
| `le16toh` / `le32toh` 显式转换 | `loopback.c:127`/`:319`、`reset.c:65`/`:109`/`:222` |
| `htons` / `NTOHS` 大端 | 南向 FPGA 帧 |

前两者在小端 ARM 上**等价**，但**风格分裂**，且 `le*toh` 缺少 `<endian.h>` 包含。

> **`le32toh` / `WEXITSTATUS` 谜题已解开**（摘要标为"推测"，平台调查给出了机制证明）：宏在预处理阶段展开，**不会在目标文件的字符串表里留下名字**；未解析的外部函数**必然**在 `.strtab` 里留下符号名。对照实验：`le32toh` / `le16toh` / `WEXITSTATUS` 在 `build/reset.o` / `loopback.o` / `log_upload.o` 中的字符串出现次数都是 **0** → 都是宏/内联，无 libc 调用。所以换 glibc/musl 不会因这三个符号编译失败。

## 7. 上手建议（Synthesize §12）

### 7.1 先读这 5 个文件（按顺序，约 1900 行，覆盖 80% 的心智模型）

1. **`src/main.c`（515 行，全读）** —— 一个文件就给出了整个系统的骨架：18+2 模块的 init 顺序（`:221-415`）、4 个跨模块全局对象的定义（`:31-39`）、**全部 TCP 粘包/半包解帧逻辑**（`on_tcp_data_received:101-164`，**解帧不在 `tcp_client.c` 里**）、3 个 TCP 回调与 2 个 UART 回调的线程归属、1Hz 主循环的两条定时状态机（`:430-479`）、cleanup 销毁序列（`:481-514`）。读完就知道「谁在哪个线程上跑、谁持有哪个全局」。

2. **`include/cpri_protocol.h`（76 行）+ `src/cpri_protocol.c`（213 行）** —— 北向协议的全部真相。**读 `:41-61` 时要特别注意 `:58` 被注释掉的告警。**

3. **`src/msg_handler.c`（399 行）** —— 从 msg_id 到业务模块的唯一路由。`:32-48` 的 14 项分发表 + `:67` 的透传前置判定 = **北向全部入口**；`:89-127`（通道建立）、`:275-399`（alarm_query/loopback/reset/calib 四个直接 `payload+4` 强转的 handler）。

4. **`src/version_manager.c`** —— 全项目最大的 .c（1262 行），也是问题最密集的文件。

5. **`src/fpga_handler.c` + `src/uart_client.c`** —— 南向的全部真相，且 `fpga_handler` 的状态缓存是**本项目锁纪律做得最好的一块**，可作为整改其他模块的参照。

### 7.2 搭起能跑的调试环境

**关键前提：本机（Windows）无法编译、无法运行、无法跑测试。** 三条可行路径：

**路径 A（推荐）：arm64 Linux 容器 / 真机**

```bash
# 依赖：gcc、make、libssl-dev（提供 libcrypto.so.1.1，注意 OpenSSL 3.x 的 SONAME 不兼容）、
#       运行时还需 curl / tar / coreutils / systemd（若测部署）
make clean && make          # ⚠️ 必须先 clean：Makefile 无头文件依赖跟踪
./antenna_mgmt ./config/antenna_mgmt.conf    # 或直接用 start.sh（它会先 make clean && make）
```

`start.sh:36` 会在未编译时自动 `make clean && make`。

**路径 B**：Linux x86 开发机——能编译，但会**静默出错**（三套字节序约定并存，零条件编译），且**测试也过不了**（静态分析确认：签名不符编译不过、同步字不匹配、`sleep(20)` 使测试在时间上不可能跑完）。

**路径 C**：只做静态分析——见下。

### 7.3 日志取证（必须加 `-a`，文件含 NUL 空洞）

```bash
cd logs
grep -ah "关键字" antenna_mgmt.log*        # -a 必须，否则报 "binary file matches"
```

**三个坑**（Gap 专题实测记录）：
1. **`-a` 必须加** —— 文件含 NUL 空洞
2. **时间戳非单调** —— BBU 通过 IE 11 反复校时，同文件混有 2025-05-09 / 2025-07-23 / 2026-xx / **2027-01-01**
3. **横跨 4 个不同 build 的 `cell_config.c`** —— 必须分 build 统计，否则数字毫无意义（OLD build 根本没有模式检查，它的 2993 次下发不能和 Build C 的拒绝数放在一个比值里）
