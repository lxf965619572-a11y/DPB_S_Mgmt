## 一、目标平台一锤定音：AArch64 小端 LP64 Linux，飞腾 D2000，本机原生编译（非交叉编译）

### 1.1 二进制层面（硬证据，非推测）

`file antenna_mgmt` 输出：

```
ELF 64-bit LSB pie executable, ARM aarch64, version 1 (SYSV), dynamically linked,
interpreter /lib/ld-linux-aarch64.so.1, for GNU/Linux 3.7.0,
BuildID[sha1]=ae73eb0e18cb134fb0f54dc234d50eb846ba4b50, with debug_info, not stripped
```

**裸 ELF 头字节独立复核**（`head -c 64 antenna_mgmt | od -An -tx1`）：

```
7f 45 4c 46 02 01 01 00 ...
     e_ident[4] = 0x02  → ELFCLASS64（64 位）
     e_ident[5] = 0x01  → ELFDATA2LSB（小端）
```

### 1.2 编译器与 ABI（DWARF producer 字符串）

```
GNU C11 7.5.0 -mlittle-endian -mabi=lp64 -g -O2 -fstack-protector-strong
```

这条串**同时出现在 `antenna_mgmt` 与 `build/main.o` 等目标文件中**，是 DWARF `DW_AT_producer`。它给出四项确定性结论：

| 结论 | 依据 |
|---|---|
| **GCC 7.5.0**，语言标准 **C11** | producer 串 |
| **`-mlittle-endian`** —— 显式小端代码生成 | 这是「代码里没有任何字节序条件编译」能够工作的**唯一前提** |
| **`-mabi=lp64`** —— LP64 数据模型 | `sizeof(int)=4`、`sizeof(long)=8`、`sizeof(void*)=8`、`sizeof(time_t)=8`。这直接决定了 `%ld` 格式串的正确性 |
| **`-g -O2`**，且 **not stripped** | 这是二进制取证能做出「同源确证」判定的原因 |

### 1.3 本机原生编译，不是交叉编译

> **这条修正了 Map 阶段摘要的说法**（见 [02 §3 自我纠错](02-方法与数据来源.md#3-自我纠错工作流内部的证伪)）。

> **结论：`make` 就是在 D2000 板子上直接跑的。仓库里不存在任何交叉编译的记录方式，x86 开发机无法凭仓库内容复现这个二进制。**

依据：`Makefile` 无交叉编译支持（无 `CROSS_COMPILE`、无 `-target`），且 DWARF 里的编译路径是目标机路径。

### 1.4 运行时依赖与最低版本

**ELF 头**：
```
e_type = 3 (ET_DYN，即 PIE)    e_machine = 183 (EM_AARCH64)    e_entry = 0x3438
class = ELF64    endian = LSB    address_size = 8
```

**`DT_NEEDED`（4 项，无 `DT_RPATH` / `DT_RUNPATH`）**：

| # | 库 |
|---|---|
| 1 | `libpthread.so.0` |
| 2 | `libcrypto.so.1.1` |
| 3 | `libc.so.6` |
| 4 | `ld-linux-aarch64.so.1` |

**`DT_VERNEED`（符号版本需求，4 项）**：

| 库 | 版本需求 |
|---|---|
| `libcrypto.so.1.1` | `OPENSSL_1_1_0` |
| `libc.so.6` | （GLIBC 各版本） |
| … | … |

⚠️ **`libcrypto.so.1.1` 是 OpenSSL 1.1 的 SONAME，OpenSSL 3.x 不兼容**（3.x 是 `libcrypto.so.3`）。这限制了可部署的发行版范围。

用到 crypto 的原因：`SHA256_Init` / `SHA256_Update` / `SHA256_Final`（`version_manager.c` 与 `firmware_package.c` 的完整性校验）。

### 1.5 发行版族系：Debian/Ubuntu 系，确定不是 RHEL/CentOS 系

**确定**。依据：库路径、`ld-linux-aarch64.so.1` 命名、systemd unit 风格。

## 三、平台相关假设的全量清点（代码里的硬编码）

### 3.1 字节序：三套约定并存，且**零条件编译**

见 [07 §2.4](07-架构与数据流.md#24-字节序三套约定并存零条件编译)。

### 3.2 `le32toh` / `WEXITSTATUS` 谜题已解开

> 摘要标为"推测"，平台调查给出了**机制证明**。

**问题**：`reset.c` 的 `le32toh` 如何解析成功？靠哪条传递包含链？换 glibc/musl 是否会编译失败？

**方法**：宏在预处理阶段展开，**不会在目标文件的字符串表里留下名字**；未解析的外部函数**必然**在 `.strtab` 里留下符号名。

**对照实验**：

| 符号 | 在 `build/reset.o` / `build/loopback.o` / `build/log_upload.o` 中的字符串出现次数 | 性质 |
|---|---|---|
| `le32toh` | **0** | 宏/内联，无 libc 调用 |
| `le16toh` | **0** | 宏/内联，无 libc 调用 |
| `WEXITSTATUS` | **0** | 宏，无 libc 调用 |

→ **答案：换 glibc/musl 不会因这三个符号编译失败**（但会因别的原因失败，见 §3.5）。

⚠️ 但 `log_upload.c:163` 用 `WEXITSTATUS` 而**全项目没有任何文件 include `<sys/wait.h>`**——这是靠传递包含侥幸成功的。

### 3.3 设备节点：PL011 命名 + 硬编码

| 设备 | 二进制中出现次数 | 使用它的源文件 | 说明 |
|---|---|---|---|
| `/dev/ttyAMA0` | 1 | `include/uart_client.h`（默认值宏）、`config/antenna_mgmt.conf:24`、`src/main.c`（`config_get_string("UART_DEVICE", ...)`） | UART，与 FPGA 通信（921600-8N1） |
| `/dev/ttyAMA2` | 1 | `src/main.c`、`include/uart_rs422_client.h`、`src/uart_rs422_client.c:239-241` | RS-422，FPGA 固件上注（921600，8O1） |

`ttyAMA*` 是 **ARM PL011** UART 的命名约定 → 又一处平台绑定。

`/dev/ttyAMA0` **可通过配置改**（`UART_DEVICE`），`/dev/ttyAMA2` 在 `uart_rs422_client.c:239-241` 有硬编码回退。

### 3.4 页大小假设：代码从不查询，而地址只兼容 ≤16KB 页（**新发现**）

全项目 `getpagesize` / `PAGE_SIZE` / `sysconf` / `_SC_PAGE_SIZE` → **零命中**。

`mmap_init` 直接把物理基址当 offset 用，**无任何对齐处理**（`src/fpga_watchdog.c:41-42`），mmap 长度硬编码 `0x1000`（`:69`、`:229`、`:440`、`:446`）。

**三个地址的整除性分析**：

```
GPIO0_BASE   0x28004000   4KB对齐:是   16KB对齐:是   64KB对齐:否（0x28004000/65536 = 10240.25）
GPIO1_BASE   0x28005000   4KB对齐:是   16KB对齐:否   64KB对齐:否（10240.3125）
PI...
```

→ **代码只兼容 ≤16KB 页**。若目标内核配 64KB 页（ARM64 支持），`mmap` 会失败或映射到错误偏移。

### 3.5 `volatile` 够不够：MMIO 访问缺内存屏障

`fpga_watchdog.c` 的 MMIO 访问只用 `volatile`，**没有 `dmb`/`dsb`/`isb` 内存屏障**。在 AArch64 上 `volatile` 只阻止编译器重排，**不阻止 CPU 乱序**——与外设寄存器交互时这是不足够的。

### 3.6 `sizeof(long)` / 指针宽度：LP64 相关代码

`include/gtypes.h:8` 的 `ULONG = unsigned long` 宽度随 ABI 变化（LP64 上 8 字节，ILP32 上 4 字节），且与 `UINT64`（`unsigned long long`）在 64 位下**同宽**。

`heartbeat.c:147-148` 的 `%ld` 格式串依赖 `sizeof(time_t)==8`（LP64 下成立）。

### 3.7 packed 结构体与非对齐访问：ARMv8 容忍，但依赖 packed 属性

`param_config.c:198`/`:207`/`:216` 三处直接强转（见 [09 §1.2](09-协议一致性.md#12-关于未对齐-uint32-陷阱的核查结论)）。ARMv8 容忍大部分非对齐访问，但依赖结构体的 `packed` 属性。

### 3.8 `localtime()` 12 处、`localtime_r()` 0 处：时区与线程双重假设

见 [08 §C-12](08-并发与锁审计.md#c-12中localtime-在-13-处跨线程并发调用且-logger-的调用点在锁外)。

（口径差异：平台调查数 12 处，并发审计 grep 数 13 处——差异来自是否计入某一处。两处都确认了 `localtime_r` **零命中**。）

## 四、让代码无法在其他平台编译/运行的完整清单

### 4.1 Windows（含 MinGW/MSVC）—— **完全不可能编译**

**20+ 项 Linux-only 依赖**，第一步就失败：`include/common.h:9` 的 `<unistd.h>`。

### 4.2 macOS —— **不能编译**

> **结论：macOS 上大约需要改 6~8 个文件才能编译，且编译通过后除了纯协议解析部分，任何硬件相关功能都不可用。**

### 4.3 其他 Linux（x86-64 / 32 位 ARM）—— **能编译，但会静默出错**

> **这是最危险的一类，因为编译器不报错。**

**x86-64 Linux（同为小端 LP64）**：

| 项 | 结果 |
|---|---|
| 能编译、能链接 | ✅（`-lcrypto -lpthread` 都有） |
| 北向 CPRI | ✅ **能正常工作**（x86-64 也是小端，`memcpy` 直读的假设成立） |
| 南向 FPGA UART / RS-422 | ✅ 也能工作（用的是可移植的 `htons`/`ntohl`） |
| **但** | ❌ `/dev/ttyAMA0`、`/dev/ttyAMA2` **不存在**（x86 上是 `ttyS*`）→ `src/uart_client.c:39` open 失败 |
| 对此的处理 | ⚠️ `src/main.c:373-375` 判定为**非致命**（"Failed to open UART de…"）→ **程序会继续跑，但没有硬件** |

**32 位 ARM**：`sizeof(long)=4` → `ULONG`、`time_t`、`%ld` 全部错位。

### 4.4 大端主机（PowerPC / MIPS BE / s390x）—— 能编译，**北向彻底不通**

`main.c:118-120` 直接 memcpy 读 `msg_length`，**零条件编译** → 大端主机上读出的长度是字节反转的垃圾值 → 粘包切分全错 → **北向彻底不通**。

### 4.5 其他 libc（musl / Alpine / uClibc）—— **大概率编译失败**

`le32toh` / `WEXITSTATUS` 不是问题（§3.2 已证），但 `libcrypto.so.1.1` 的 SONAME、`<sys/wait.h>` 的传递包含、以及 glibc 特有扩展会导致失败。
