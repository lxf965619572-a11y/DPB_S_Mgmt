## 1. 工作流结构

分析由一个 28-agent 工作流完成（ID `wf_b1c46e35-fd3`），四阶段串行 + 阶段内并行：

```
Map（11 agent，并行）        →  按子系统逐个摸底，行号级
    ↓
Cross-check（5 agent，并行） →  跨切面调查（线程/协议/平台/一致性/覆盖度）
    ↓                          其中 2 个 failed
Gap（1 critic + 8 agent）    →  critic 评估覆盖度，派生 9 项深挖专题
    ↓                          其中 1 项 failed 后重跑
Synthesize（1 agent）        →  架构综合
```

## 2. 证据等级

本报告对每条结论标注了它的证据强度。请特别注意区分：

| 等级 | 含义 | 例子 |
|---|---|---|
| **硬证据 / 确证（proven）** | 字节级、可复现验证 | 32 个 `.o` 的 `.debug_info` 与二进制逐字节相同；`.text` 掩掉重定位点后零差异；ELF 头 + DWARF producer 判定平台 |
| **日志实证** | 57MB 现场部署日志中的量化计数与端到端配对案例 | 去重陷阱触发 541 次；180 次 `wait_for_antenna_mode_cycle` 成功、总耗时 267600 ms；9 次进程内时钟回跳全部自愈 |
| **代码逐行确认** | 读源码得到的确定事实，附行号 | `channel_setup.c:336-340` 版本不匹配只 `LOG_WARN`；`reset.c:254` 的 `system()` 被注释 |
| **grep 穷举** | 全项目搜索，分母明确 | `pthread_create` 在 `src/` 下只有 8 个命中，全部列出（无遗漏） |
| **静态推理** | 基于代码逻辑的推演，未经运行验证 | 竞态窗口的可达性论证、单位换算的自洽性判定 |
| **推测** | 证据不足的猜测，报告中明确标注 | 部署形态与仓库不一致（`二进制取证`附带发现，标为推测） |

**重要**：协议一致性调查的一个方法论前提是——**仓库内不存在任何协议规格书 / ICD**（`docs/api`、`docs/guides`、`docs/images`、`docs/procedurefile` 四个目录全空）。因此该调查以**部署日志为最高权威**，用真实运行数据反推协议语义。这意味着：凡涉及"协议应该是什么样"的结论，都是**从实现和日志归纳的，不是从规格书核对的**。

## 3. 自我纠错（工作流内部的证伪）

工作流的跨切面阶段主动证伪了 4 条 Map 阶段的摘要论断。这类纠错值得单独记录，因为它们说明摘要层可能存在未被发现的其他误差：

| 原论断 | 证伪结果 |
|---|---|
| 心跳超时检测因时钟回跳而「永久失效」 | **证伪一半**：机制成立（`heartbeat.c:139` 有符号相减），但唯一能产生回跳的路径会立刻调 `heartbeat_start()` 重新基准化，失效窗口只有几微秒。日志实测 9 次进程内回跳全部在 16 行内自愈 |
| `g_recv_buffer` / `g_recv_offset` 可能被多线程访问 | **修正**：确认只有 T2（TCP recv 线程）访问，主循环完全不碰 |
| 本机是交叉编译产物 | **修正**：`make` 就是在 D2000 板子上直接跑的，仓库里不存在任何交叉编译的记录方式 |
| `wait_for_antenna_mode_cycle` 阻塞导致心跳超时占 50% | **修正**：实测是 **8/25**，不是 50/50；影响面比想象的小 |

另外两处对前序材料的复核结论：
- 「三个身份字段只被回填、无一处参与判断」→ **坐实，无一处反例**
- 「遥测字段 17 个零读取者」→ **完全正确，一个不差，无遗漏也无误报**

## 5. ⚠️ 缺口声明

如实列出本次分析**没有覆盖**的部分。问题清单应理解为**下界**，不是全集。

### 5.1 工作流自身的失败项（2 个 agent 无产出）

| 失败项 | 本该回答什么 | 缺口后果 |
|---|---|---|
| **`e2e-flow`**（端到端流程） | 完整的跨子系统时序：一条消息从 TCP 收包到 FPGA 应答再到北向回复的全链路 | 数据流 A~E 是从 11 份子系统摘要**拼出来的**，没有独立 agent 做过完整时序核查。**数据流之间的相互影响存在覆盖空白**——例如固件上注期间业务面会怎样（Gap 专题虽提到"上注期间不停业务、不暂停 1s 状态轮询、不暂停 3s 喂狗"，但没有做完整时序推演） |
| **`completeness`**（覆盖度核查） | "还有哪些维度没查" | 由 `completeness-critic` **部分补上**：它评估了已有材料的维度覆盖，判定哪些已做到行号级、哪些是缺口，并据此派生了 Gap 阶段的 9 项深挖。但 critic 本身也 failed 过一次后才成功，且它的定位是「派生新专题」而非「穷举未覆盖面」。**"还有哪些没查"这个问题没有被系统回答** |
