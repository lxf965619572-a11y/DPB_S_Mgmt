### P0-2 心跳基准改用单调时钟（`src/heartbeat.c:47,120,138,154`；`include/heartbeat.h:15`）

```c

```

```c
/* src/heartbeat.c 新增内部辅助 */
static inline int64_t mono_sec(void) {
```

## 8. 系统性建议（项目级约定）

### 8.1 时钟使用约定

> **建立「超时判定一律用 `CLOCK_MONOTONIC`，只有需要墙上时钟语义（日志、上报时间戳、文件名）才用 `CLOCK_REALTIME`」的项目约定。**

项目里**已经有正确范例**（`src/uart_rs422_client.c:326-349`），把它抽成 `include/common.h` 里的公共辅助函数，避免每个模块各写一遍。

### 8.2 RTC 回写

> **`clock_settime` 成功后回写 RTC（`hwclock -w` 或 `ioctl(RTC_SET_TIME)`）**，否则每次重启都会退回 `2025-05-09`，日志顺序永久错乱，告警过滤持续被击穿。

**当前全项目无任何 RTC 回写代码。**

这是 §7 排序里 #2「上游根因」的核心——日志里 ±458 天的跳变全部源于此。

### 8.3 日志加单调时钟列

> **`src/logger.c:192-194` 增加单调时钟列**，例如 `[2026-08-15 11:13:43|+12345.678]`，这样即便墙上时钟被改写，**日志仍可恢复真实先后顺序**。

当前日志顺序错乱已经给取证造成了实质困难（见 [11 §0](11-现场日志实证.md#0-取证的三个坑必须先说) 坑 2）。

### 8.4 错误处理契约

> **这是最根本的一条。** [05 §总体定性结论](05-P2-一般级问题.md#总体定性结论) 的四条证据链证明：**不是能力问题，是没有跨模块的错误处理契约。**

双标证据最能说明这点：同一个项目里 `cpri_encode_message` **19/19 检查**、`fpga_encode_message` **12/12 检查**、`pthread_create` **8/8 检查**、`fpga_firmware_injector.c` 整个状态机每步都校验并重试——**证明团队完全有能力写正确的错误处理**。但紧挨着 `cpri_encode_message` 检查的下一行 `tcp_client_send` **94.7% 被忽略**。

建议的具体约定：
1. **任何返回 `int` 的函数，`return SUCCESS` 必须意味着"操作确实成功了"**，而不是"函数执行完了"
2. **任何返回 `int` 的调用，返回值必须被检查或被显式 `(void)` 转换并注释原因**
3. **"命令已发出"不等于"操作已成功"**——需要区分 `SUCCESS_SENT` 和 `SUCCESS_CONFIRMED`
4. 用 `-Wunused-result` + `__attribute__((warn_unused_result))` 标注关键 API，让编译器帮忙
5. 参照 `fpga_handler` 的锁纪律和 `fpga_firmware_injector` 的状态机——**它们是本项目的正面样本**

### 8.5 单一可信来源

当前状态：**代码、文档、测试、Python 模拟端四源互相矛盾（32 项）**，且 6 份文档全部过期或失实。

建议：
1. 把 6 份失实文档**标注为"历史归档，不代表当前实现"**，或删除
2. 修 `mock_bbu_server.py`（载荷不带 TLV IE 头，联调测试全部无效）
3. 修或删除 `fpga_injector_test.py`（十个维度全部不符）
4. **向协议方索取 ICD**——这是最根本的解法，见 §9

**前置约束（决定方案可行性）**：7 次 mismatch 的 `file_name`/`file_version` **全空串**，`file_path`/`file_len`/`file_time` 也从未被填过有效值 →

> **"PAAU 依据 IE 14 自行发起下载"在当前 BBU 实现下走不通**（拿不到任何构造 msg 21 或 FTP 拉取的参数）；且协议上 msg 21 是 BBU→PAAU，`cpri_protocol.h:10-45` 全表无 PAAU 发起的下载请求。

**因此最小改动应是"可观测+可追溯"而非"自动触发下载"，分三级：**

**Level 1（最小、零风险、约 10 行）：记入状态并落盘**

`channel_setup.c` 顶部加文件级 static（该文件目前**零 static 变量**）：`static version_check_state_t g_ver_check;`，在 `:336-340` 的 else 分支里记录 mismatch 的时间、`file_name`、`file_version`、`result`，并落盘到 `/opt/vendor/version_check.log`，同时触发 `alarm_manager` 的告警。

Level 2 / Level 3 见完整分析（需 BBU 侧配合，超出单侧改动范围）。
