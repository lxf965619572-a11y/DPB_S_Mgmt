# A. 安全：远程命令执行与零认证

## A1. shell 命令注入（root 级远程命令执行）

**代码事实**

| 位置 | 代码 |
|---|---|
| `src/version_manager.c:86` | `popen("tar -xzf \"<tar_path>\" -C \"<dest_dir>\"")` |
| `src/version_manager.c:718` | `system("rm -rf \"<version_dir>\"")` |
| `src/version_manager.c:521-524` → `:528` | curl 命令拼接后 `popen` |
| `src/log_upload.c:133-137` → `:142` | curl 命令拼接后 `popen` |

`tar_path` 由 BBU 提供的 `file_name` 构成（`version_manager.c:656-657` 拼出）；`version_dir` 由 `VERSION_BASE_DIR` 与 `task->version` 拼成，而 `task->version` 直接来自 BBU 的 `ie_req->file_ver`（`:993` / `:1014`）；`store_path` / `file_name` / `file_path` 同样来自 BBU 且未经净化就拼入 curl 命令。

**机理**：全部只用双引号包裹，**未做任何 shell 元字符转义**，也无字符白名单。

**后果**：`file_name` 里含 `";`、`$( )` 或反引号，即可在 PAAU 上以 **root** 权限执行任意命令——`scripts/antenna-mgmt.service` 里设的是 `User=root`。

> Gap 阶段的原始评级把这条列在「次级但未进 Top 10」，并注明：**「若把安全影响计入，这一条应排 P0。」** 本报告采纳该意见，列为 A1。

**修复**：~30 行。改用 `fork` + `execvp` 数组传参（不经 shell），或对 `file_name` / `file_ver` / `store_path` 做严格字符白名单（`[A-Za-z0-9._-]`）。

## A2. 路径穿越 + 任意文件上注

**代码事实**：`version_manager.c:993` / `:1014` 直接取 `ie_req->file_ver`，`:695-696` 拼出 `version_dir`，**无任何字符白名单或路径穿越检查**。

**机理**：`file_ver` 若为 `../..` 之类，拼出的 `version_dir` 会逃出 `/opt/vendor/versions/`。

**后果**：
1. `:718` 的 `system("rm -rf \"<version_dir>\"")` 变成**任意目录删除**
2. 任意 `.bin` 可被上注到 FPGA

**修复**：与 A1 同批处理。白名单校验 + `realpath` 后确认仍在 `VERSION_BASE_DIR` 之内。

## A3. 北向链路零认证

**代码事实**：北向 TCP 链路**完全没有**认证、鉴权、完整性校验或加密。

源 IP 也不校验：`msg_handler.c:316/339/362/377` 四处的审计日志里，`source_ip` 是 `config_get_string("BBU_IP", "unknown")`——**从配置文件读的常量，不是实际对端地址**。真实对端地址从未被获取过（无 `getpeername` 调用）。

**后果**：任何能连到 PAAU TCP 端口的主机，都等同于 BBU。审计日志记录的是假源地址，事后无法追溯实际攻击来源。

**修复**：
- P1（~15 行）：`tcp_client.c:111-114` 连接成功后调 `getpeername` + `inet_ntop` 存入 `client->peer_ip[INET_ADDRSTRLEN]`（`include/tcp_client.h:15` 加字段），四处审计日志改用它。可选强化：与 `g_config.bbu_ip` 比对，不一致则告警（防 ARP 欺骗 / 端口抢注）。
- 真正的认证需要协议层改动，要 BBU 侧同步升级。

## A4. 入站身份字段无一处参与判断

**代码事实**（grep 穷举，已复核）：全项目对 `header.paau_id` / `header.bbu_id` / `header.port_num` 的读取，**只被回填进出站报文，无一处参与任何判断**。

> Gap 阶段对前序材料的复核结论：**「坐实，无一处反例。」**

`serial_num` 同样：出站递增，**入站零校验**（无连续性检查、无去重）。

**后果**：报文寻址语义形同虚设。`port_num` 是纯装饰字段，且存在两套互不关联的语义。

**修复**（P0，5 行）：在 `src/msg_handler.c:56 msg_handler_dispatch` 的 `:60` 之后、`:62` 之前插入：

```c
int local_id = config_get_int("PAAU_ID", 0);
if (msg->header.paau_id != local_id) {
    LOG_WARN("Msg for paau_id=%u, not us (%d) — drop", msg->header.paau_id, local_id);
    return ERROR_INVALID_PARAM;
}
```

> ⚠️ 需先与 BBU 侧约定"广播值"（如 `0xFF` 表示全体 PAAU），以免破坏现有 `PAAU_ID=0` 部署。
>
> 顺带：`include/reset.h:21` / `include/loopback.h:28` 定义的 `RESET_ERR_PERMISSION`、`src/reset.c:158`（告警码 70002）/ `src/loopback.c:179`（60002）已预留错误码和告警码，但**全项目无一处 return**。可在 paau_id 比对失败时返回它，顺带激活已预留的告警。

## A5. 透传通道可裸写 FPGA

**代码事实**：msg 231-240 的调用链——

```
src/msg_handler.c:67
  → src/transparent_msg.c:285  fpga_send_raw(...)
    → src/fpga_handler.c:365-374
      → uart_client_send  （直写 /dev/ttyAMA0）
```

**前置条件**：仅需 TCP 连通。IE 1602 必须存在（`transparent_msg.c:187`），内容非全零（`:282`）。

**后果**：**绕过全部 FPGA 命令封装**。BBU（或任何冒充 BBU 的主机）可以构造任意字节流直接写给 FPGA，不受 `fpga_handler` 里任何命令格式、参数范围、状态机检查的约束。

**附带**：`transparent_msg.c:295-306` 的自动回显是**无条件**的，构成反射原语，且会把攻击者的 1024 字节原样弹回。

**修复**（P0）：把 `fpga_send_raw(...)` 改成走安全路径（白名单命令码 + 长度上界），或至少加：
- P2（15 行）：`:282-290` 加令牌桶限速；`:295-306` 自动回发改为可配置

## A6. `is_transparent_message` 形参截断

**代码事实**：`include/transparent_msg.h:129` 与 `src/transparent_msg.c:49` 的形参是 `uint16_t msg_id`，而 `msg_id` 在线上是 32 位。

**机理**：`msg_id = 65536 + 231` 会被截断成 `231`，落入透传分支。

**后果**：审计误标 + 意外走透传路径。

> 可达性论证成立，但 Gap 阶段修正了落点：「**落点与前序材料描述的不同（重要修正）**」。

**修复**（P0，6 处签名）：`include/transparent_msg.h:129` + `src/transparent_msg.c:49` 改 `uint32_t msg_id`；同时 `:108 transparent_msg_parse` 与 `:257 handle_transparent_bbu_to_paau` 的 `uint16_t msg_id` 一并改；`include/transparent_msg.h:74` 的 `transparent_parse_result_t.msg_id` 与 `:99`/`:109` 原型同步。

## A7. msg_id 无白名单

**代码事实**：`src/cpri_protocol.c:174` 附近，`msg_id` **无范围校验**，任意值都会被 dispatch。

## A8. 入站 payload 长度零校验

**代码事实**：三处只查了 `!msg->payload`，不查长度就强转结构体指针读字段：

| 位置 | 目标结构体 | 实际大小 |
|---|---|---|
| `src/log_upload.c:289` | `ie_xxx_t` | 204 字节 |
| `src/version_manager.c:962` | `ie_version_download_req_t` | 291 字节 |
| `src/version_manager.c:1079` | `ie_version_activate_ind_t` | 45 字节 |

另有 4 个 handler 同样无前置检查：`src/log_upload.c:306`、`src/version_manager.c:973` / `:981` / `:1085`。

**机理**：`cpri_decode_message` 的长度校验**形同虚设**——`:178` 发现 `msg_length` 与实收长度不符时只打日志不拒绝；`main.c:123` 只校验 `msg_length` 在 15~8192 之间。而 `param_config.c:163` 更进一步：用**线上的 `msg_length`** 而非实际 `payload_len` 计算解析范围 → 可越界读。

**后果**：
1. BBU 发一个 `payload_len=5` 的 Msg 21，PAAU 会把内存池里的**残留字节**当作 `file_path` / `version_num` / `store_path` 使用
2. 配合 A1/A2，残留字节内容可被攻击者预先布置

**修复**（P0，3×3 行）：补 `msg->payload_len < sizeof(ie_xxx_t)` 检查，**照抄 `src/msg_handler.c:285/308/331` 已有的正确写法**。

# B. 可用性：远程 DoS

## B1. TLV 下界校验缺失 → 接收线程死循环

**代码事实**：全项目共 **6 处** TLV 遍历循环，其中 **5 处**缺 `ie_len < 4` 下界校验（只有 `src/transparent_msg.c:145-150` 一处写法正确）：

| # | 位置 | msg_id | 循环不变式 | 推进语句 |
|---|---|---|---|---|
| 1 | `src/status_query.c:76` | — | `req_offset + ie_len > request->payload_len` | `:233 req_offset += ie_len` |
| 2 | `src/param_config.c:190` | 61 | `offset+4>payload_len` / `offset+ie_length>payload_len` | `:235 offset += ie_length` |
| 3 | `src/channel_setup.c:243` | — | — | `:397` |
| 4 | `src/cell_config.c:639` | 195 | — | `:674` |

> Gap 阶段对前序清单的复核结论：**「不完整，少 1 处死循环」**——即前序只发现 3 处，普查补出第 4 处。

**机理**：`ie_len == 0` 时——
- 边界检查 `offset + 0 > payload_len` 为假，不 break
- 推进语句 `offset += 0`，offset 不变
- 循环条件永远成立

`status_query.c:81` 的 `ie_data_len = ie_len - 4` 还会下溢成 65532，但**没被用来做边界检查**。

**后果**：BBU 一个 **4 字节畸形 IE** 即可让 `tcp_recv_thread` **100% CPU 死循环**，北向服务全停。FPGA 看门狗在独立线程继续喂狗，**不会救**。

**修复**（P0，3~8 行）：

```c
if (ie_len < 4 || offset + ie_len > payload_len) break;   /* 照抄 transparent_msg.c:145-150 */
```

## B2. 死循环后进程无法优雅退出

**代码事实**：`tcp_client_stop` 对 recv 线程做 `pthread_join`。

**机理**：recv 线程卡在 B1 的死循环里，`running = false` 的检查点永远到不了 → `pthread_join` 永久阻塞。

**后果**：进程无法优雅退出，只能 `kill -9`。而 `kill -9` 会跳过全部 cleanup，且**喂狗线程被强杀 → 可能触发硬件复位**（见 [08 §C-1](08-并发与锁审计.md)）。

**修复**：修 B1 即可消除触发条件。另建议给 recv 加 `SO_RCVTIMEO`（见 P2 socket 选项），让循环有周期性退出检查点。

---

## B3. 重组缓冲溢出丢消息且不告警

**代码事实**：TCP 粘包重组缓冲在溢出时直接丢弃。

**机理**：溢出时不做"先处理已完整消息再丢残余"，而是整段丢弃；只打一行 `LOG_ERROR`，**不上报告警**。

**日志实证**：`logs/antenna_mgmt.log.1` 有 **3 次** `Receive buffer overflow`。

**后果**：消息丢失且 BBU 无从知晓。

**修复**：先尽量处理已完整的消息再丢弃残余，或扩大重组缓冲使其严格大于单次 recv 上限。

> **附带发现（Gap 专题 2）**：重组缓冲区**跨连接不复位**。断连重连后，上一条连接的残留半包会被当成新连接的开头解析。

# C. 正确性：假成功掩盖真实失败

## C1. 复位动作被注释掉，仍返回成功

**代码事实**（`src/reset.c`）：

```c
:252   LOG_INFO("Service will restart in 2 seconds...");   /* 假日志 */
:253   sleep(2);                                            /* 真睡 */
:254   // system("systemctl restart antenna-mgmt.service &");   ← 被注释掉
...
:275   return SUCCESS;
```

`:239-240` 还留着更早版本的注释痕迹。软复位分支的**净效果** = 发一帧 `FPGA_MSG_PHASE_RESTORE(0)` + 睡 2 秒 + 打一条假日志 + `return SUCCESS`。

硬复位同样（`:272`，`return SUCCESS` 在 `:275`）。

**后果**：BBU 下发复位后，PAAU 只 `sleep(2)` 就报成功。BBU 以为已重启并继续下发配置。**任何需要靠复位恢复的故障都恢复不了，且现场无从察觉。**

**修复**（P0，~6 行）：取消注释 + 检查 `fpga_send_phase_restore` 返回值 + 失败时 `return ERROR_GENERAL`。

> 注：在消息处理线程里 `sleep(2)` 本身也是问题（见 [08 §D.3 持锁阻塞](08-并发与锁审计.md)），应一并移出 recv 线程。

## C2. 固件上注：激活应答在上注启动之前发出

**代码事实**（`src/version_manager.c`）：


## C3. IE 14 版本核对结果被丢弃

**代码事实**（`src/channel_setup.c:301-344`，**本次已用当前源码逐行复核**）：

```c
case IE_TYPE_VERSION_CHECK: {
    if (ie_data_len >= 1) {
        uint8_t version_type = ie_data[0];
        LOG_INFO("Version check IE received: type=%u (0=软件, 1=固件)", version_type);

        if (ie_data_len >= 285 && version_type == 1) {
            /* memcpy 解析 result(4) / file_path(200) / file_name(16)
                      / file_len(4) / file_time(20) / file_version(40) */
            LOG_INFO("Firmware version check: result=%u, file=%s, version=%s",
                     result, file_name, file_version);
            if (result == 0) {
                LOG_INFO("Firmware version matches");
            } else {
                LOG_WARN("Firmware version mismatch, may need update");   /* ← :339 到此为止 */
            }
```

**证实**：`result != 0` 只打一条 `LOG_WARN`，**无任何后续动作**——不触发升级、不上报告警、不回送 BBU、不影响任何状态。

Gap 阶段的评价：**「证实且比描述更糟」**。补充事实：
- `:305` 的 `LOG_INFO` 在 `type=0`（软件版本）时也执行，但软件分支**完全不解析**任何字段
- **IE 14 撞号成立**，两处布局完全一致
- 固件版本**无其他上报途径**（复核前序断言，全部证实）
- 升级后 IE 6 **不会变**——软件和固件都不会（比背景假设更强）

**后果**（回答 Gap 专题的问题 8）：**现场人员不拆机、不用示波器，无法从软件侧查到 FPGA 当前固件版本——这是完整的可观测性缺口。**

**12 环节闭环表**的结论：版本闭环在「谁发现版本不对」这一环就断了。

**修复**：见 [12-修复路线图](12-修复路线图.md) §6 最小修复建议。

## C4. 小区配置去重陷阱（现场触发 541 次）

> ⚠️ **本条的修复已被回退，当前代码仍有此缺陷。** 详见 [02 §4.2](02-方法与数据来源.md) 和 [README §2](README.md)。

**代码事实**（当前 `src/cell_config.c`，已逐行复核）：

| 步骤 | 行号 | 行为 |
|---|---|---|
| 步骤1 | `:377` | `if (!mode_check_passed)` — 天线不在业务/频谱监测模式 |
| | `:402-415` | **仍然写入本地表**，置 `active = true`，日志 `"Freq saved locally (not sent)"` |
| | `:418-419` | `*result = CONFIG_RESULT_FAILURE; break;` |
| 步骤2 | `:423` | `bool need_send_to_antenna = true;` |
| | `:426-441` | 去重循环：只比 `dl_center_freq` / `ul_center_freq` / `beam_bandwidth` |
| | `:432` | 命中 → `need_send_to_antenna = false` |
| 步骤5 | `:528-532` | else 分支：只调 `update_tx_control()`，然后 `*result = CONFIG_RESULT_SUCCESS` |

去重循环的三个缺陷：
1. **不比 `beam_id`** — 不同波束的同频配置会被误判为重复
2. **不查是否真下发过** — 步骤1 留下的"僵尸记录"（`active=true` 但从未发给 FPGA）会被当成有效配置
3. **注释与实现不符** — `:425` 注释写「全局检查」，`:426-430` 实现只扫 `freqs[cell_idx]`（当前小区）

`has_any_freq()`（`:13-21`）同样只看 `active && freq_count > 0`，**不看是否真下发过** → 僵尸记录会支撑 `update_tx_control()` **保持发射开启**。

**触发路径**：
```
待机模式下 BBU 下发频点
  → 步骤1 模式检查失败
  → 存本地表（active=true）+ 回 FAILURE
  → BBU 认为失败，重发同一频点
  → 步骤2 去重命中（比对僵尸记录）
  → need_send_to_antenna = false
  → 步骤5 else 分支：不下发 FPGA，却回 SUCCESS
  → BBU 以为配好了，天线实际没配
```

**第二条触发路径**（案例 C）：遥测不可用时同样落入此路径。

**日志实证**（57MB，Gap 专题 8）：

| 待验证项 | 结论 |
|---|---|
| 拒绝分支是否真的存本地表 | ✅ 成立，顺序无误 |
| 去重是否只扫当前小区（注释说"全局"） | ✅ 成立，且不比较 `beam_id` |
| else 分支是否回 SUCCESS 且不下发 | ✅ 成立 |
| **现场是否真实触发** | ✅ **找到 3 个端到端配对案例，其中 2 个是铁证** |

三个案例：
- **案例 A**（2026-08-12 00:51:07 → 00:52:03，base log 15808–16820）：陷阱路径完整执行
- **案例 B**（2026-08-12 11:04:42 → 11:37:45，base log 25265–27581）：**铁证，无巧合可乘**——进程内 `Sending freq/band` = **0**，却回了 **15 次** `result=0`（cell_id=2, DL=2180100, UL=1980000, BW=100，**16 个 beam 全军覆没**）
- **案例 C**（2026-08-15 11:01:02 → 11:19:05，base log 34108–54071）：**规模最大的铁证**——`Sending freq/band` = **0**，却回了 **510 次** `result=0`

**总计：现场真实发生至少 541 次。**

> **取证陷阱**（必须注意）：这份 57MB 日志横跨 **4 个不同 build** 的 `cell_config.c`。按 build 分段统计才能得到正确结论——Build C（部署版）的完整模板清单与次数已单列，Build B 有一个更露骨的假成功。

**修复**：恢复 `rollback_backup/cell_config.{c,h}.modified`（修复已写好，被回退了）。两个改法任选，**推荐 (a)**：

- **(a) 门控失败时不要写本地表**：删掉 `:402-415` 的存储逻辑，直接 `*result = CONFIG_RESULT_FAILURE; break;`。让 BBU 的重发能被正常处理，而不是被自己上一次失败留下的脏数据去重掉。
- **(b) 给条目加 `sent_to_antenna` 标志**：去重循环 `:426-441` 增加 `&& g_cell_mgr.freqs[cell_idx][i].sent_to_antenna` 条件，且跳过 `beam_id == freq_cfg->beam_id` 的自己。

> `rollback_backup/` 里的修复版采用的是 (b) 的强化形式：结构体加 `sent_to_antenna` 字段，抽出 `store_freq_info(slot, freq_cfg, sent_to_antenna)` 辅助函数，`has_any_freq()` 也一并只看 `sent_to_antenna`，从根上消除僵尸记录支撑发射的问题。

另外 `:425-426` 的注释与实现不符需明确取其一（真全局 or 改注释）。

## C5. 心跳超时兜底被 `heartbeat_start()` 清零绕过

**代码事实**：
- `src/heartbeat.c:143` `bbu_heartbeat_miss_count++`
- `src/heartbeat.c:146` `>= HEARTBEAT_TIMEOUT_COUNT`（20 次，约 60 秒）才判超时
- `src/heartbeat.c:121` 收到心跳时 `bbu_heartbeat_miss_count = 0`（正常）
- **`heartbeat_start()`（`:40-53`）也会清零计数与时间基准**
- `src/msg_handler.c:94` → `:124` → `src/heartbeat.c:47`：**msg 2 每次都调 `heartbeat_start()`**

**机理**：msg 2 是「同一条连接内被高频重复发送」，不是「每次连接一次」。日志实证：
- 单连接内 **110 条** msg 2，**无任何断连日志**
- 另一片段：单连接内 **67 条**，含 1~2 秒的极短间隔
- 29 字节短包，**间隔精确 7 秒**，9 连发（`logs/antenna_mgmt.log` 15785~16685）
- `serial_num` **连号**证明是 BBU 主动重发（`logs/antenna_mgmt.log` 32801~32843）

每次 msg 2 都把 `miss_count` 抹掉 → 计数永远到不了 20 → **60 秒超时兜底形同虚设**。

**日志实证**：**已在现场真实触发**（`miss_count=15` 被抹掉）。

**后果**（`src/main.c:461-478`）：主循环的超时处理是**单向失效**的——兜底本该在 BBU 失联时复位连接，但计数被反复清零，永远不触发。

**修复**（P0-1）：`heartbeat_start()` 不得清零丢失计数。最小改动是拆成两个语义：

```c
/* 仅在 heartbeat_enabled 由 false 变 true 时才初始化计数与时间基准 */
int heartbeat_start(void) {
    pthread_mutex_lock(&g_heartbeat_mgr.mutex);
    bool was_enabled = g_heartbeat_mgr.heartbeat_enabled;
    g_heartbeat_mgr.heartbeat_enabled = true;
    if (!was_enabled) {
        g_heartbeat_mgr.paau_heartbeat_count = 0;
        g_heartbeat_mgr.bbu_heartbeat_miss_count = 0;
        /* ... 时间基准 ... */
    }
    pthread_mutex_unlock(&g_heartbeat_mgr.mutex);
    return SUCCESS;
}
```

**配套修复**（P0-3）：msg 2 幂等短路（`src/msg_handler.c:89-128` + `src/main.c:145-148`），避免高频重复的 msg 2 反复执行副作用。

## C6. 通道建立应答 `result` 恒为字面量 0

**代码事实**：
- `src/msg_handler.c:102`：`result` 传的是**硬编码 0**
- `src/channel_setup.c:296` / `:359` / `:387`：3 个 `fpga_send_*` 返回值**全部未检查**
- `src/channel_setup.c:400`：`channel_setup_handle_config` 末尾**无条件 `return SUCCESS`**

**叠加因素**：
- `src/fpga_handler.c:167`：`fpga_send_beam_num` 忽略**第一帧**的发送结果，两帧之间**无原子性**（只有 `:179` 第二帧的结果被返回）。若指令波束数帧失败而业务波束数帧成功，FPGA 会进入 `n1` 旧值 + `n2` 新值的**混合状态**
- `src/main.c:145-148`：**无条件**置 `g_channel_established = true`，不看 dispatch 结果

**后果**：FPGA 未收到工作模式 / 波束数 / CPRI 模式配置时，BBU 仍认为建链成功并转入业务。而 `:124` 已 `heartbeat_start()`，**双方状态机永久错位**。叠加 `fpga_handler.c:167` 的内部忽略，可能只下发了一半波束配置。

**修复**（P1，~25 行）：`channel_setup_handle_config` 聚合 3 个 `fpga_send_*` + `clock_settime` 的结果，传给 `create_response` 的 `result` 形参——**形参已存在**，只是没人往里传真值。

## C7. 校准结果查询硬编码成功

**代码事实**：
```c
src/status_query.c:220    calib_resp[0] = 0;  /* 0=成功 */     ← 完全不读 FPGA
src/phased_array_calib.c:126-134    result = fpga_send_calibration();   ← 只是 UART write 的返回值
```

**关键**：遥测帧里 `calib_result` 字段**是存在且已被解码的**——

- `fpga_protocol.c` 已把它 `memcpy` 进 `status->data`

**后果**：硬件明明上报了校准失败，PAAU 仍然告诉 BBU 校准成功。这是本子系统里**最明确的桩实现**。BBU 侧任何依赖此结果的逻辑都会误判。相控阵可能长期带错误相位/幅度工作，**波束指向偏差且无人知晓**。

**修复**（P1，~25 行）：下发后轮询 `fpga_status.data.calib_result`（byte 85），超时则报失败。

```c
calculate_sha256(download_path, checksum);
```

# D. 并发：确认的严重竞态 / UB

> 完整审计见 [08-并发与锁审计](08-并发与锁审计.md)。这里只列标为「严重」的 7 项。

## D1. 退出路径 use-after-free

3 个 **detached** 线程 + `logger_close()` **无锁** + `pthread_mutex_destroy` 在**用锁**上执行。

`main.c:481-514` 的 cleanup 序列销毁 mutex 和 logger，而 detached 线程可能仍在运行并使用它们。

## D2. TCP 停止序列 tid 无同步覆写

`recv_thread` 的 tid 无同步被覆写，T2 可在 `state_mutex` **被销毁后**仍使用它，且**旧 recv 线程永不 join**。

配套问题（P2）：`g_channel_established` 四线程无锁读写，且 T2 尾部回调可覆盖 T1 刚建立的新连接状态（C-9）；`tcp_client_stop` 与 `tcp_connect_to_server` 的竞争可在 cleanup 期间新建连接（C-10）。

## D3. `version_manager` 的 `in_progress` 闸门被自己的 memset 打掉

**代码事实**（`src/version_manager.c`）：

```c
:977    g_download_task.in_progress = true;    /* 持锁 */
:978    pthread_mutex_unlock(...);             /* 解锁 */
:987    memset(&g_download_task, 0, sizeof(...));   /* ← 把 in_progress 也清零了 */
...                                              /* 中间还有 strncpy / config_get_string */
:1040   g_download_task.in_progress = true;    /* 锁外重新置 */
```

**后果**：`:987` 到 `:1040` 之间是一段**无锁且标志为 false 的窗口**，可并发两个下载线程操作同一全局与同一目录。

**叠加**：`:762` 下载线程**无锁**写 `task->version`（`task` 即全局 `g_download_task`），而主线程可能同时在 `version_handle_download_request` 里读/写同一结构 → **对同一全局结构的三方竞争**。

## D4. `tcp_client_send` 无发送互斥

**代码事实**（`src/tcp_client.c`）：`:218-226` 只用 `state_mutex` 保护了「取 sockfd」这一小段，真正的 `:229-236` 分包 `send` 循环**完全无锁**（grep 确认 `tcp_client.h` 里没有发送锁）。

**后果**：
1. **5 个线程**可在同一 socket 上**交织字节流**
2. sockfd 快照后解锁 → **fd 复用写入错误目标**

**附带**：`:230 send(sockfd, …, 0)` 未带 `MSG_NOSIGNAL`，且无 `signal(SIGPIPE, SIG_IGN)` → 对端 RST 后写入会收到 SIGPIPE，**默认处置是终止进程**。`Restart=always` 会拉起来，但期间喂狗线程停止 → 可能触发硬件复位。修复：`src/main.c:422` 旁加一行 `signal(SIGPIPE, SIG_IGN)`。

## D5. 二次 `pthread_join` 同一 tid（日志实证）

TCP 与 UART 各一处。

**UART 侧**（`src/uart_client.c:385-390`）：`uart_client_close` join 完 `recv_thread` 和 `poll_thread` 后**没有把这两个 `pthread_t` 字段清零**，而 `src/main.c:497-498` 是：

```c
uart_client_close(&g_uart_client);
uart_client_destroy(&g_uart_client);    /* destroy 里再 join 一次同样的 tid */
```

**后果**：未定义行为。**已有日志实证**。

## D6. signal handler 自死锁

signal handler 内有 **async-signal-unsafe** 调用，会在 `g_log_mutex` 上**自死锁**。

这是全项目**唯一真实存在的死锁**——锁序图全部单向，**无锁序环**（见 [08 §D](08-并发与锁审计.md)）。

**放大因素**（C-13）：`g_log_mutex` 临界区覆盖**阻塞文件 I/O**，是全局串行化点，也放大了 C-6 的死锁窗口。

## D7. watchdog destroy 未初始化 mutex / 二次 destroy

`src/fpga_watchdog.c:436 fpga_watchdog_destroy`：
- `:439-448` 直接 `munmap` 两段 MMIO 并把指针置 NULL
- `:456` 销毁 mutex
- **全程不看 `enabled` 也不 join thread**

正常路径 `main.c:485` 先 stop 后 destroy 是安全的，但：
- (a) 若 stop 因任何原因没被调用或提前返回，喂狗线程会在 3 秒后访问**已 unmap 的内存** → 段错误（use-after-unmap）
- (b) init 失败路径会 destroy **未初始化**的 mutex

**同类问题**（C-16）：`alarm_manager_init` 失败路径也会 destroy 未初始化的 mutex——`:87 pthread_mutex_init` 失败时 `:89` 返回，`main.c:255-258` 判定失败后 `goto cleanup`，而 cleanup 段 `main.c:502` **无条件**调 destroy。
