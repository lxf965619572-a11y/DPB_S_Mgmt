## 1. 结论

**不建议按当前状态交付。**

代码在功能骨架上是完整的（18+2 模块装配、北向 CPRI 类协议、南向两套串口、固件上注全链路都写了），也能在目标板上跑起来（57MB 现场日志证明它确实在长期运行）。但存在三类会直接影响交付的问题：

| 类别 | 判断 | 关键依据 |
|---|---|---|
| **安全** | 阻断 | root 级远程命令执行路径现成可用（2 处命令注入 + 北向零认证 + 透传裸写 FPGA） |
| **可用性** | 阻断 | BBU 一个 4 字节畸形 IE 即可让接收线程死循环，且进程无法优雅退出 |
| **正确性** | 阻断 | 复位 / 校准 / 环回三个运维动作是假的；版本升级闭环断裂；带宽单位无法自洽 |
| **健壮性** | 高风险 | 16 项确认的竞态 / UB，其中 7 项标为「严重」 |
| **可维护性** | 高风险 | 6 份文档全部过期或失实；单元测试与源码签名不符，编译不过 |
| **工程质量** | 系统性 | 假成功不是个别疏忽：315 个函数体里 38 个假实现、20 处假成功语义 |

## 3. 五类最该先看的问题

### 3.1 安全：root 级远程命令执行

北向 TCP 链路**完全没有认证、鉴权、完整性校验或加密**，且 `paau_id` / `bbu_id` / `port_num` 三个身份字段在全项目**无一处参与判断**（只被回填进出站报文）。源 IP 也不校验——审计日志里的 `source_ip` 是从配置文件读的常量，不是实际对端地址。

在此前提下，有三条现成的攻击链：

| # | 动作 | 入口 | 前置条件 | 后果 |
|---|---|---|---|---|
| 1 | **任意 FPGA 帧裸写** | msg 231-240 → `transparent_msg.c:285 fpga_send_raw()` → `uart_client_send` 直写 | 仅需 TCP 连通 | 绕过全部 FPGA 命令封装 |
| 2 | **软件版本切换 + 服务重启** | msg 31 (ver_type=0) | 仅需 TCP 连通 | `system("systemctl restart ...")`，在消息处理线程内 |
| 3 | **shell 命令注入** | `version_manager.c:86 popen("tar -xzf \"<tar_path>\" ...")`；`:718 system("rm -rf \"<version_dir>\"")` | `file_name` / `file_ver` 由 BBU 提供，只用双引号包裹，**零转义** | `";`、`$()`、反引号即可在 PAAU 上以 **root** 执行任意命令（systemd unit 里 `User=root`） |

`file_ver` 还不做路径穿越检查，`../..` 可让 `rm -rf` 逃出 `/opt/vendor/versions/`。

### 3.2 可用性：远程 DoS + 无法优雅退出

**4 处** TLV 遍历循环缺 `ie_len < 4` 下界校验（6 处循环里只有 `transparent_msg.c:145-150` 一处写法正确）：

- `status_query.c:76` + `:233`
- `param_config.c:190` + `:235`
- `channel_setup.c:243` + `:397`
- `cell_config.c:639` + `:674`

`ie_len == 0` 时 `offset += ie_len` 加 0，循环条件永远成立 → **TCP recv 线程 100% CPU 死循环**。

连锁后果：FPGA 看门狗在独立线程继续喂狗，不会救；`tcp_client_stop` 的 `pthread_join` 永久阻塞，进程无法优雅退出，只能 `kill -9`。

### 3.3 正确性：三个运维动作是假的

| 动作 | 代码事实 | 后果 |
|---|---|---|
| **复位** | `reset.c:254` 软复位的 `system("systemctl restart ...")` **被注释掉**；`:252` 仍打印 "Service will restart in 2 seconds..."，`:253` 真的 `sleep(2)`，`:275` 返回 SUCCESS | BBU 以为已重启并继续下发配置；任何需要靠复位恢复的故障都恢复不了，现场无从察觉 |
| **校准** | `status_query.c:220` 硬编码 `calib_resp[0] = 0; /* 0=成功 */`，完全不读 FPGA。而遥测帧里 `calib_result` 字段**存在且已被解码**（`fpga_protocol.h:100`） | 硬件明明上报校准失败，PAAU 仍告诉 BBU 成功。相控阵可能长期带错误相位/幅度工作，波束指向偏差且无人知晓 |
| **环回** | `loopback.c:333-343` 环回结果 = UART `write` 返回值；`test_period`/`port_number`/`beam_number` 已在 `:82`/`:88` 校验但**从未下发** | 环回测试实际不执行 |

**版本升级闭环断裂**：`version_manager.c:1142` 的激活应答在 `:1156` 的固件上注启动**之前**发出，`:1157-1160` 显式容忍注入失败。此后无论 SHA256 失败、FPGA 拒绝、重传耗尽还是 CRC 不过，都只落在本地日志。

**IE 14 版本核对结果被丢弃**：`channel_setup.c:336-340`，固件版本不匹配只 `LOG_WARN("Firmware version mismatch, may need update")`，无任何后续动作。（本次已用当前源码复核确认。）

**带宽单位无法自洽**：这是单位换算链审计里结论最严重的一项。同一个 S 频段、同一时期，两个小区用**相差 1000 倍**的 bw 值同时配置（`BW=20000` 492 次 / `BW=100` 391 次）。四种候选单位解释逐一对照实测值后，**不存在任何一种能让数据自洽**。而 FPGA 侧**没有拒绝机制**——协议层无 ACK/NACK，唯一的应答回调 `main.c:167-172` 是空壳 `(void)data;`。

### 3.4 并发：16 项确认的竞态 / UB

全部 8 个 `pthread_create` 点已穷举，共享状态矩阵与锁保护逐一判定。**7 项标为「严重」**：

| 编号 | 问题 |
|---|---|
| C-1 | 退出路径：3 个 detached 线程 + `logger_close()` 无锁 + `pthread_mutex_destroy` 在用锁 → use-after-free |
| C-2 | TCP 停止序列：`recv_thread` tid 无同步被覆写，可在 `state_mutex` 销毁后仍被使用，旧 recv 线程永不 join |
| C-3 | `version_manager` 的 `in_progress` 闸门被自己的 `memset` 打掉（`:977` 置 true → `:978` 解锁 → `:987` memset 清零 → `:1040` 锁外重设） |
| C-4 | `tcp_client_send` 无发送互斥，5 个线程可在同一 socket 上交织字节流；sockfd 快照后解锁 → fd 复用写入错误目标 |
| C-5 | 二次 `pthread_join` 同一 tid（TCP 与 UART 各一处），**日志实证** |
| C-6 | signal handler 内 async-signal-unsafe 调用，会在 `g_log_mutex` 上自死锁 |
| C-7 | `fpga_watchdog_destroy` 与 init 失败路径：destroy 未初始化的 mutex / 二次 destroy |

**死锁分析结论**：锁序图全部单向，**无锁序环**；真实存在的死锁只有一处（C-6 信号处理器自死锁）。逐函数核对漏解锁、回调重入均已做。

**做得对的部分**：`fpga_handler` 的 FPGA 状态缓存锁纪律良好，是本项目做得最对的一块。`g_serial_num` 全部递增点都走了锁，无绕过。

### 3.5 心跳与阻塞：现场已真实触发

**去重陷阱**（P0-4）：待机模式下下发频点会「存本地表 + 回 FAILURE」，BBU 重发同一频点时去重命中 → **不下发 FPGA 却回 SUCCESS**。

日志实证：**现场真实发生至少 541 次**，找到 3 个端到端配对案例，其中 2 个是铁证（进程内 `Sending freq/band` = 0，却分别回了 15 次和 510 次 `result=0`）。

> ⚠️ 该缺陷的修复版存在于 `rollback_backup/`，但**当前 `src/cell_config.c` 已回退**，缺陷仍在。详见 [README §2](README.md)。

**阻塞拖死北向**：`cell_config.c:239-314 wait_for_antenna_mode_cycle` 最长阻塞 5 秒，跑在 **TCP 接收线程**上（`:510` 调用）。这与已保存的项目记忆一致：CPRI 接收循环是单线程的，handler 里任何阻塞都会拖死整条 BBU 链路。

日志实证：180 次成功调用，总耗时 267600 ms（平均 1.49 秒）；25 次心跳超时事件中 **8 次**可归因于此（不是先前推测的 50/50）。决定性物证：超时后 socket 里排着 BBU 的心跳——**是 PAAU 自己没去读，不是 BBU 没发**。

**心跳兜底被绕过**：`heartbeat_start()` 会清零 `bbu_heartbeat_miss_count`。而 msg 2 每次都调它 → 高频重复的 msg 2（日志实测：单连接内 110 条，间隔精确 7 秒）不断把计数抹掉，60 秒超时兜底形同虚设。

**时钟回跳**：`heartbeat.c:139` 的 `elapsed = now - last` 是有符号相减，回跳后 `:142` 的 `elapsed >= HEARTBEAT_INTERVAL_SEC` 长期为假。但「永久失效」这个定性被**证伪了一半**：唯一能产生回跳的路径（msg 2 设完时钟后）会立刻调 `heartbeat_start()` 重新基准化，所以失效窗口只有几微秒；日志实测 9 次进程内回跳全部在 16 行内被重新基准化。
