# FPGA固件注入逻辑分析（修正版）

## 发送/接收逻辑流程

### 正常流程（同步阻塞）
```
第N段数据传输：
1. 构造数据帧N
2. 调用 uart_rs422_send_and_wait()
   ├─ 发送数据帧N到串口
   ├─ 阻塞等待FPGA应答（最多15秒）
   └─ 收到应答并返回
3. 解析应答结果
4. 如果成功(0x00)：
   ├─ current_segment++
   ├─ 延迟50-100ms（实际不必要）
   └─ 进入下一轮循环，发送第N+1段
5. 如果失败(0xFF)：
   ├─ 延迟500ms
   ├─ 回退文件指针
   └─ 重发第N段
```

**关键结论**：
- ✅ 必须等到收到FPGA应答才会发送下一帧
- ✅ 不存在"发送太快导致FPGA缓冲区溢出"的问题
- ❌ 段间延迟（50-100ms）是多余的，只会拖慢传输速度

## "发送失败"的真正原因

### 原因1：接收超时（ERROR_TIMEOUT）- 最可能
```
发送数据帧 → 等待15秒 → 没收到应答 → 超时返回
```

**根本原因**：
1. **串口接收缓冲区溢出**（重点怀疑）
   - 环形缓冲区只有5120字节
   - 如果FPGA在等待期间发送了其他数据（状态上报、心跳等）
   - 或者之前的残留数据未清理
   - 导致应答帧被覆盖或丢失

2. **FPGA处理超过15秒**
   - 写Flash操作慢
   - 擦除坏块需要额外时间
   - FPGA内部状态异常

3. **FPGA应答帧在传输中丢失**
   - 电磁干扰
   - 串口硬件故障

### 原因2：应答帧校验失败（ERROR_GENERAL）
```
发送数据帧 → 收到应答 → 校验和不匹配 → 解析失败
```

**根本原因**：
1. **串口奇校验配置不一致**（重点怀疑）
   - 代码中 `use_parity = 0;` 被注释掉
   - 如果FPGA期望8O1，但实际使用8N1
   - 每个字节的第8位会被误认为是数据位
   - 导致数据错误，校验和不匹配

2. **电磁干扰**
   - 数据位翻转

3. **波特率不精确**
   - 采样错误

### 原因3：应答帧格式错误（ERROR_GENERAL）
```
发送数据帧 → 收到应答 → 包头错误/长度异常 → 解析失败
```

**根本原因**：
- 环形缓冲区中混入了其他数据
- 包查找器状态异常

## 应答0xFF的真正含义

**重要理解**：
- ✅ 串口通信正常（收到了应答）
- ✅ 应答帧格式正确（能解析出0xFF）
- ❌ **FPGA端数据校验失败**

**FPGA拒绝的原因**：
1. **发送的数据帧校验和不匹配**（最可能）
   - 串口发送时数据被破坏
   - 奇校验配置错误导致数据位错误
   
2. **段号不连续或重复**
   - 重传逻辑错误
   
3. **数据长度与协议不符**

4. **FPGA内部Flash写入失败**

## 段间延迟的必要性分析

**当前代码**：
```c
/* 成功后延迟50-100ms */
if (task->current_segment == 1) {
    usleep(100000);  /* 100ms */
} else {
    usleep(50000);   /* 50ms */
}
```

**分析**：
- 由于是同步等待应答，FPGA应答时已经处理完这一段
- **段间延迟是多余的**，只会拖慢传输速度
- 如果FPGA需要时间处理，它应该延迟应答，而不是我们主动等待

**结论**：段间延迟应该去掉或大幅减少（如5-10ms用于日志输出）。

## 修正后的解决方案

### 方案1：发送前清空接收缓冲区（关键）
```c
/* 在发送数据帧前清空接收缓冲区，避免残留数据干扰 */
rBufFlush(&g_recv_ctx.rbuf);
tcflush(task->uart_client->fd, TCIFLUSH);  /* 清空内核缓冲区 */

/* 发送数据帧并等待应答 */
int ret = uart_rs422_send_and_wait(...);
```

### 方案2：去掉不必要的段间延迟
```c
/* 成功,继续下一段 */
task->current_segment++;
task->retry_count = 0;

/* 不需要段间延迟，FPGA应答时已经处理完 */
// 删除 usleep(50000);

return SUCCESS;
```

### 方案3：确认并启用奇校验
```c
/* 取消注释，启用奇校验 */
use_parity = (strstr(client->device_path, "ttyAMA2") != NULL);
// 删除 use_parity = 0;
```

### 方案4：增大环形缓冲区
```c
typedef struct {
    uint8_t rd_buf[1024];
    uint8_t rbuf_storage[10240];  /* 从5120增加到10240 */
    RBUF rbuf;
    // ...
} uart_recv_context_t;
```

### 方案5：动态超时（首段和末段更长）
```c
/* 根据段位置调整超时 */
uint32_t timeout_ms;
if (task->current_segment == 0 || 
    task->current_segment == task->total_segments - 1) {
    timeout_ms = 30000;  /* 首段和末段30秒 */
} else {
    timeout_ms = 15000;  /* 中间段15秒 */
}

uint32_t old_timeout = task->uart_client->timeout_ms;
uart_rs422_set_timeout(task->uart_client, timeout_ms);

int ret = uart_rs422_send_and_wait(...);

uart_rs422_set_timeout(task->uart_client, old_timeout);
```

## 优先级排序

1. **最高优先级**：确认奇校验配置（方案3）
2. **高优先级**：发送前清空缓冲区（方案1）
3. **中优先级**：增大环形缓冲区（方案4）
4. **低优先级**：去掉段间延迟（方案2）
5. **可选**：动态超时（方案5）

## 排查步骤

1. **确认串口配置**：与FPGA端保持一致（最重要）
   - 检查FPGA是8N1还是8O1
   - 修改代码匹配

2. **启用详细日志**：观察是超时还是校验失败
   - 记录每次失败的错误码
   - 记录失败时的段号

3. **发送前清空缓冲区**：避免残留数据干扰

4. **增大环形缓冲区**：防止溢出

5. **监控应答时间**：记录每段的实际应答时间
   - 找出哪些段应答慢
   - 是否有规律

## 预期效果

- 消除因缓冲区溢出导致的超时
- 消除因奇校验不一致导致的0xFF
- 加快传输速度（去掉不必要的延迟）
- 提供更准确的错误诊断
